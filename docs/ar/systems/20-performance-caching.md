# 20 — Performance & Caching Strategy

> **بادئة القواعد:** `PF-` · **الحالة:** إلزامي · **المالك:** Full-stack
> **المرجع الأعلى:** [`../../en/00-PROJECT-RULES.md`](../../en/00-PROJECT-RULES.md) · **نسخة النظام الحاكمة:** [`../../en/systems/20-performance-caching.md`](../../en/systems/20-performance-caching.md) · هذه ترجمة عربية متزامنة.
> **يحقق المبدأ:** `CORE-014` (Edge/cache first)

---

## 0. هدف الأداء الحاكم

> **الطلب العام المعتاد لموقع منشور يجب أن يُخدَم من الـ CDN/Edge، أو من الـ renderer بقراءة واحدة محسوبة — لا بسلسلة استعلامات لكل section.**

ولماذا هذا شرط وجود لا تحسين: عدد الزيارات العامة **أكبر بعدة مراتب** من عمليات لوحة التحكم. لو ضرب كل زائر قاعدة البيانات، فالمنتج يسقط عند أول عميل ناجح — أي أن **نجاح عميلنا يصبح سبب عطلنا**، وهذا أسوأ نموذج فشل ممكن.

---

## 1. طبقات الـ Cache

```
الزائر
  ↓
① CDN / Edge          ← معظم الطلبات تنتهي هنا
  ↓ (miss)
② Renderer + cache التطبيق
  ↓ (miss)
③ Redis  (تهيئة الموقع · خريطة الدومين)
  ↓ (miss)
④ PostgreSQL          ← أقل عدد ممكن من الطلبات يصل هنا
```

**`PF-001` (MUST):** كل طبقة لها مفتاح واستراتيجية إبطال معرَّفان صراحةً وموثَّقان.

**`PF-002` (MUST NOT):** ممنوع الاعتماد على انتهاء الصلاحية (TTL) وحده لبيانات يعدّلها المستخدم ويتوقع رؤية تعديله فورًا (`QJ-051`).

---

## 2. تخزين المواقع المنشورة

**`PF-010` (MUST):** مفتاح الـ cache للصفحة المنشورة: **`hostname + path + publishedRevisionId`** (`RP-051`).

> **لماذا `publishedRevisionId` في المفتاح:** الإبطال يصبح **تلقائيًا ومجانيًا**. النسخة الجديدة = مفتاح جديد. لا حاجة لمسح دقيق، ولا خطر لعرض محتوى قديم، ولا سباق بين النشر والإبطال.

**`PF-011` (MUST):** الإبطال عند النشر يشمل **الموقع المتأثر فقط** (`RP-052`). المسح الشامل ممنوع (`QJ-052`).

**`PF-012` (MUST):** خريطة `hostname → site_id` مخزَّنة بـ TTL قصير/متوسط وإبطال صريح عند كل تغيير (`DN-051`).

**`PF-013` (MUST):** تعطل طبقة الـ cache **لا يُسقط المواقع** — رجوع لقاعدة البيانات مع حد للمعدل وتنبيه (`DN-053`).

**`PF-014` (MUST):** حماية من انهيار الـ cache للمفاتيح الساخنة (`QJ-053`).

---

## 3. مسار الرندر الساخن

**`PF-020` (MUST NOT):** **ممنوع N+1** في مسار الرندر (`CORE-066`). هذه القاعدة الأكثر أهمية في هذا الملف.

**`PF-021` (MUST):** عدد الاستعلامات لعرض صفحة منشورة **ثابت**، لا يعتمد على عدد الصفحات أو الأقسام.

> هذا ما تحققه اللقطة المكتفية بذاتها (`RP-005`): قراءة واحدة تجلب كل ما يلزم.

**`PF-022` (MUST):** أي استعلام جديد في المسار الساخن يُراجَع بـ `EXPLAIN ANALYZE` قبل الدمج (`DM-043`).

**`PF-023` (MUST):** مسار الرندر **لا يستدعي أي طرف ثالث** بشكل متزامن. لا AI، لا بريد، لا DNS، لا أي شيء خارجي.

> **لماذا:** بطء طرف ثالث يتحول فورًا إلى بطء في مواقع كل عملائنا.

**`PF-024` (MUST):** مكوّنات الـ sections لا تجلب بيانات (`CE-060`).

---

## 4. الأصول

**`PF-030` (MUST):** الأصول بروابط **immutable** مع content hash وعمر cache طويل (`AS-041`).

**`PF-031` (MUST):** الصور بالحجم المناسب للسياق — لا خدمة الأصل الكامل في صورة مصغرة (`AS-031`).

**`PF-032` (MUST):** WebP/AVIF مع بديل مناسب (`AS-032`).

**`PF-033` (MUST):** الخطوط: مجموعة محدودة، `font-display: swap`، تحميل مسبق للحرِج (`FE-072`).

**`PF-034` (MUST):** الصور بأبعاد صريحة لمنع قفز التخطيط (`CE-064`).

---

## 5. تخزين لوحة التحكم

**`PF-040` (MUST NOT):** **ممنوع** تخزين بيانات لوحة تحكم حساسة بطريقة قد تخلط المستأجرين (`MT-043`).

**`PF-041` (MUST NOT):** ممنوع `Cache-Control: public` على أي استجابة تحتوي بيانات خاصة.

**`PF-042` (MUST):** تخزين لوحة التحكم على مستوى العميل (طبقة الجلب) بإبطال صريح بعد كل تعديل، لا بـ TTL وحده.

**`PF-043` (MUST):** الحسابات الثقيلة (الاستخدام، تجميعات الـ analytics) محسوبة مسبقًا لا عند كل طلب (`BE-053`, `AN-044`).

---

## 6. قاعدة البيانات

**`PF-050` (MUST):** الفهارس تبدأ بعمود الـ scope (`MT-032`)، وتُضاف لاستعلامات حقيقية فقط (`DM-023`).

**`PF-051` (MUST):** كل قائمة لها حد أقصى مفروض في الخادم (`DM-041`, `API-041`).

**`PF-052` (MUST):** الترقيم cursor-based (`API-040`).

**`PF-053` (MUST):** مجمّع الاتصالات محسوب ومحدود لكل خدمة (`IN-053`).

**`PF-054` (MUST):** الاستعلامات البطيئة مراقَبة ومسجَّلة، وتُراجَع دوريًا.

**`PF-055` (SHOULD):** عند النمو، القراءات الثقيلة تنتقل لنسخ قراءة (read replicas) — بقياس لا بتوقع.

---

## 7. الميزانيات والقياس

**`PF-060` (MUST):** ميزانيات صريحة ومراقَبة:

| ما يُقاس | الميزانية |
|---|---|
| كمون الـ API (p95) | < 500ms (`OB-030`) |
| عدد استعلامات رندر الصفحة | ثابت (لا يعتمد على عدد الأقسام) |
| حجم حزمة لوحة التحكم | حد مراقَب في CI (`FE-074`) |
| حجم JS الموقع المنشور | أدنى ما يمكن — ويفضّل صفرًا للأقسام الثابتة |
| معدل إصابة الـ cache للمواقع المنشورة | مرتفع ومتصاعد |

**`PF-061` (MUST):** الأداء **مقاس لا مفترض**. «يبدو سريعًا على جهازي» ليس قياسًا.

**`PF-062` (MUST):** اختبار حمل للمسارات الحرجة قبل الإطلاق: رندر المواقع · دفعات النشر · استيعاب الـ analytics.

**`PF-063` (MUST NOT):** **ممنوع التحسين المبكر بلا قياس.** حسّن ما يُقاس أنه بطيء، لا ما تظنه بطيئًا.

> **لماذا:** التحسين بلا قياس يضيف تعقيدًا يصعّب الصيانة، وغالبًا يستهدف المكان الخطأ — بينما العنق الحقيقي يبقى.

## 8. الأنماط الممنوعة

| # | النمط | لماذا هو خطر |
|---|---|---|
| 1 | N+1 في مسار الرندر | ينهار عند أول عميل ناجح |
| 2 | مفتاح cache بلا `revisionId` | محتوى قديم بعد النشر |
| 3 | مسح شامل عند كل نشر | انهيار أداء لكل المواقع |
| 4 | استدعاء طرف ثالث في مسار الرندر | بطء خارجي يصيب كل العملاء |
| 5 | مكوّن section يجلب بيانات | يكسر الـ caching والأداء |
| 6 | `Cache-Control: public` لبيانات خاصة | تسريب بين المستخدمين |
| 7 | مفتاح cache بلا scope | تسريب بين المستأجرين |
| 8 | TTL وحده لبيانات يعدّلها المستخدم | «تعديلي لم يظهر» |
| 9 | قائمة بلا حد أقصى | استجابة ضخمة تُسقط الخدمة |
| 10 | `OFFSET` للقوائم الكبيرة | بطء متزايد + نتائج غير متسقة |
| 11 | حساب ثقيل عند كل طلب | بطء مزمن يتفاقم |
| 12 | صور بلا أبعاد | قفز تخطيط يضر التجربة والـ SEO |
| 13 | تحسين بلا قياس | تعقيد بلا فائدة |
| 14 | pool غير محدود | استنزاف اتصالات = عطل كامل |

## 9. الاختبارات المطلوبة

**`PF-070` (MUST):** اختبار عدد الاستعلامات: رندر صفحة بـ 5 أقسام وبـ 40 قسمًا → **نفس عدد الاستعلامات**.

**`PF-071` (MUST):** اختبار الإبطال: النشر → الطلب التالي يعكس المحتوى الجديد فورًا.

**`PF-072` (MUST):** اختبار العزل في الـ cache: مفاتيح مستأجرين مختلفين لا تتقاطع أبدًا.

**`PF-073` (MUST):** اختبار حمل: رندر المواقع تحت حمل متزامن ضمن ميزانية الكمون.

**`PF-074` (MUST):** اختبار تدهور لطيف: تعطل الـ cache → المواقع تظل تُخدَم.

**`PF-075` (MUST):** اختبار ميزانية الحزم في CI.

## 10. Definition of Done — Performance

- [ ] لا N+1 في أي مسار ساخن.
- [ ] عدد استعلامات الرندر ثابت.
- [ ] مفتاح الـ cache يتضمن `publishedRevisionId`.
- [ ] الإبطال صريح ومستهدف للموقع المتأثر.
- [ ] لا استدعاء طرف ثالث في مسار الرندر.
- [ ] الأصول بروابط immutable وحجم مناسب.
- [ ] لا cache عام لبيانات خاصة.
- [ ] كل مفتاح cache يحمل scope و TTL.
- [ ] حماية من انهيار الـ cache للمفاتيح الساخنة.
- [ ] تدهور لطيف عند تعطل الـ cache.
- [ ] الفهارس تبدأ بعمود الـ scope و`EXPLAIN` مراجَع.
- [ ] حد أقصى للقوائم وترقيم cursor-based.
- [ ] الحسابات الثقيلة محسوبة مسبقًا.
- [ ] ميزانيات الأداء مقاسة في CI.
- [ ] اختبار حمل للمسارات الحرجة.

---

## 11. ما يحتاج ADR

- تغيير استراتيجية العرض (SSR ↔ ISR ↔ static ↔ edge).
- إضافة نسخ قراءة أو تقسيم قاعدة البيانات.
- إضافة طبقة cache جديدة.
- تغيير مزوّد الـ CDN.
- تغيير استراتيجية الإبطال.
