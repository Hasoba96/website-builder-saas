# 11 — Billing & Entitlements

> **بادئة القواعد:** `BE-` · **الحالة:** إلزامي · **المالك:** Backend
> **المرجع الأعلى:** [`../../en/00-PROJECT-RULES.md`](../../en/00-PROJECT-RULES.md) · **نسخة النظام الحاكمة:** [`../../en/systems/11-billing-entitlements.md`](../../en/systems/11-billing-entitlements.md) · هذه ترجمة عربية متزامنة.

## 0. القاعدة الأساسية

> ### `BE-001` (MUST NOT)
> **ممنوع** أن يسأل الكود «هل المستخدم Pro؟» في عشرات الأماكن.
> كل سؤال عن ميزة أو حد يمر عبر **Entitlement Service مركزية واحدة**.

```ts
can(tenant, 'custom_domain')            → boolean
limit(tenant, 'websites')               → 5
limit(tenant, 'ai_generations_monthly') → 100
usage(tenant, 'storage_bytes')          → 1_240_000_000
```

**لماذا هذه القاعدة قبل كل شيء:**

فحص اسم الخطة مبعثر في الكود يعني أن إضافة خطة جديدة تتطلب تعديل عشرات الملفات، وأن عرضًا ترويجيًا لعميل واحد مستحيل، وأن كل مكان منسي يصبح إما ثغرة (ميزة مدفوعة مجانية) أو باقًا (عميل دفع ولا يحصل على ما دفع مقابله). مع نمو الخطط تصبح هذه الفوضى غير قابلة للإصلاح.

```ts
// ❌ ممنوع — مبعثر وهش ومستحيل التطوير
if (org.plan === 'pro' || org.plan === 'business') { ... }
if (subscription.planCode !== 'free') { ... }

// ✅ صحيح — مصدر واحد للحقيقة
if (await entitlements.can(ctx, 'custom_domain')) { ... }
```

## 1. نموذج الـ Entitlements

**`BE-010` (MUST):** كل ميزة أو حد له **`feature_key` ثابت وموثَّق**. الخطط تربط المفاتيح بالقيم، لا العكس.

| `feature_key` | النوع | مثال |
|---|---|---|
| `websites` | حد | 1 / 5 / 25 |
| `pages_per_website` | حد | 5 / 20 / غير محدود |
| `custom_domain` | منطقي | false / true |
| `remove_branding` | منطقي | false / true |
| `ai_generations_monthly` | حد | 10 / 100 / 1000 |
| `storage_bytes` | حد | 500MB / 5GB / 50GB |
| `team_members` | حد | 1 / 5 / 25 |
| `leads_retention_days` | حد | 30 / 365 / 1095 |
| `analytics_history_days` | حد | 7 / 90 / 365 |

**`BE-011` (MUST):** الحد غير المحدود يُمثَّل بقيمة صريحة معروفة (`null` أو `-1`) **موثَّقة ومتسقة**، لا برقم كبير عشوائي.

**`BE-012` (MUST):** إضافة ميزة جديدة = إضافة `feature_key` جديد + قيمته في **كل** الخطط القائمة. **ممنوع** ترك خطة بلا قيمة معرَّفة.

> **لماذا:** المفتاح الناقص يعني سلوكًا غير معرَّف — وسيُفسَّر إما كـ «ممنوع» فيغضب عميلًا دافعًا، أو كـ «مسموح» فيعطي ميزة مدفوعة مجانًا.

**`BE-013` (MUST):** الـ Entitlement Service تدعم **تجاوزات على مستوى المستأجر** (overrides) فوق قيمة الخطة.

> **لماذا:** ستحتاج يومًا أن تعطي عميلًا مهمًا حدًا أعلى، أو تعوّض عميلًا عن عطل. بلا آلية للتجاوز، الحل الوحيد يصبح تعديلًا يدويًا خطرًا في قاعدة البيانات.

**`BE-014` (MUST):** ترتيب الحل: **تجاوز المستأجر ← قيمة الخطة ← الافتراضي الآمن (الأقل سماحًا)**.

## 2. الفرض (Enforcement)

**`BE-020` (MUST):** الفرض **server-side دائمًا** (`CORE-004`). الواجهة تعرض الحدود وتحسّن التجربة، ولا تفرض شيئًا.

**`BE-021` (MUST):** الفحص يتم عند **نقطة التنفيذ الفعلية**، لا في الواجهة فقط ولا في نقطة واحدة بعيدة.

**`BE-022` (MUST):** فحص الحدود المعتمدة على العدد **ذرّي مع الإنشاء** — لا فحص ثم إنشاء في خطوتين منفصلتين.

```ts
// ❌ حالة سباق: طلبان متزامنان يتجاوزان الحد معًا
const count = await websites.countInOrg(orgId);
if (count >= limit) throw new LimitExceeded();
await websites.create(...);

// ✅ ذرّي: قيد في قاعدة البيانات أو قفل أو فحص داخل الـ transaction
await db.transaction(async (tx) => {
  const count = await websites.countInOrgForUpdate(tx, orgId);
  if (count >= limit) throw new LimitExceeded('websites', limit);
  await websites.create(tx, ...);
});
```

**`BE-023` (MUST):** الخطأ يحمل **المفتاح والحد والاستخدام الحالي** ليتمكن العميل من فهم الموقف والتصرف:

```json
{
  "error": {
    "code": "PLAN_LIMIT_EXCEEDED",
    "featureKey": "websites",
    "limit": 5,
    "current": 5,
    "message": "لقد بلغت الحد الأقصى لعدد المواقع في خطتك الحالية"
  }
}
```

**`BE-024` (MUST):** الحدود الشهرية لها **نافذة إعادة تعيين واضحة** مرتبطة بدورة الاشتراك، لا بالشهر الميلادي — إلا إذا وُثِّق العكس صراحةً.

**`BE-025` (MUST):** الفحص في الـ worker أيضًا، لا عند الجدولة فقط (`MT-044`).

## 3. الاشتراكات ودورة الحياة

**`BE-030` (MUST):** حالات الاشتراك من مجموعة محصورة:

```
trialing → active → past_due → canceled
                 ↘ paused
active → active (تجديد)
```

**`BE-031` (MUST):** فشل التجديد يدخل **مهلة سماح (grace period) موثَّقة** قبل أي تقييد.

> **لماذا:** بطاقة منتهية أو فشل بنكي عابر أمر شائع تمامًا. إسقاط موقع عميل فورًا عند أول فشل دفع يضر عميلًا كان سيدفع بعد ساعات — ويخسر العلاقة نهائيًا.

**`BE-032` (MUST):** خلال مهلة السماح: الموقع **يظل يعمل**، والتنبيه واضح في لوحة التحكم وبالبريد.

**`BE-033` (MUST NOT):** **ممنوع حذف بيانات** عند تراجع الخطة أو إلغاء الاشتراك (`CORE-083`).

**`BE-034` (MUST):** تراجع الخطة يتبع سياسة موثَّقة:

| الحالة | السلوك الإلزامي |
|---|---|
| المواقع أكثر من حد الخطة الجديدة | تُقرأ وتظل منشورة؛ لا إنشاء جديد حتى النزول للحد |
| التخزين أكثر من الحد | لا رفع جديد؛ لا حذف تلقائي |
| الدومين المخصص لم يعد ضمن الخطة | سياسة موثَّقة (تعطيل مؤجل بعد إشعار) — لا قطع مفاجئ |
| الأعضاء أكثر من الحد | لا إضافة جديدة؛ لا إزالة تلقائية |

**`BE-035` (MUST):** الإلغاء يبقي الخدمة حتى **نهاية الفترة المدفوعة**، ثم ينتقل لحالة مقيَّدة مع فترة احتفاظ قبل أي حذف.

**`BE-036` (MUST):** كل تغيير في حالة الاشتراك يُسجَّل في `audit_logs`.

## 4. Webhooks من مزوّد الدفع

**`BE-040` (MUST):** الـ webhook من مزوّد الدفع هو **مصدر الحقيقة** لحالة الدفع — لا نتيجة الواجهة ولا إعادة التوجيه بعد الدفع.

> **لماذا:** المستخدم قد يغلق المتصفح قبل إعادة التوجيه. الدفع نجح والحساب لم يُفعَّل — تذكرة دعم مضمونة وعميل غاضب محق.

**`BE-041` (MUST):** **التحقق من التوقيع إلزامي** قبل أي معالجة. بلا توقيع صالح = رفض فوري.

> **لماذا:** بلا تحقق، أي شخص يعرف عنوان الـ webhook يرسل «تم الدفع» ويحصل على خطة مدفوعة مجانًا.

**`BE-042` (MUST):** المعالجة **idempotent**. المزوّدون يعيدون إرسال الأحداث عند الشك — وهذا سلوك طبيعي لا استثناء.

**`BE-043` (MUST):** الأحداث قد تصل **خارج الترتيب**. المعالجة تعتمد على **الطابع الزمني أو رقم الإصدار** في الحدث، لا على ترتيب الوصول.

> **لماذا:** معالجة حدث «تم الإلغاء» القديم بعد حدث «تم التجديد» الأحدث يلغي اشتراكًا نشطًا لعميل دافع.

**`BE-044` (MUST):** حدث غير معروف يُسجَّل ويُتجاهل بأمان **مع رد `200`** — لا فشل يجعل المزوّد يعيد المحاولة إلى ما لا نهاية.

**`BE-045` (MUST):** فشل المعالجة يذهب لطابور إعادة المحاولة ثم DLQ **مع تنبيه فوري**. فشل webhook دفع ليس خطأً عاديًا — هو مال.

**`BE-046` (MUST):** كل webhook مستلَم يُسجَّل بمعرّف الحدث وحالة المعالجة، للتوفيق والتدقيق.

## 5. قياس الاستخدام

**`BE-050` (MUST):** الاستخدام يُقاس **في أنظمتنا**، لا بالاعتماد على مزوّد الدفع.

**`BE-051` (MUST):** الاستخدام الحالي متاح للمستخدم في لوحة التحكم مقابل حده.

**`BE-052` (MUST):** التنبيه عند الاقتراب من الحد (مثلًا 80%) **قبل** بلوغه.

**`BE-053` (MUST):** حسابات الاستخدام الثقيلة (التخزين مثلًا) تُجمَّع دوريًا وتُخزَّن، ولا تُحسب في كل طلب.

## 6. المال في الكود

**`BE-060` (MUST):** المبالغ **أعداد صحيحة بأصغر وحدة** + رمز عملة (`CORE-068`). **ممنوع `float`** تحت أي ظرف.

**`BE-061` (MUST):** أي حساب مالي (ضريبة، خصم، تناسب زمني) يتم بحساب صحيح، وقاعدة التقريب موثَّقة ومختبَرة.

**`BE-062` (MUST):** الأسعار تُقرأ من مصدر واحد. **ممنوع** رقم سعر مكتوب داخل الكود.

**`BE-063` (MUST NOT):** **ممنوع** تخزين أي بيانات بطاقة أو حساب بنكي في أنظمتنا. المزوّد يحتفظ بها، ونحن نحتفظ بمرجعه فقط.

## 7. الأنماط الممنوعة

| # | النمط | لماذا هو خطر |
|---|---|---|
| 1 | فحص اسم الخطة مبعثر في الكود | فوضى غير قابلة للإصلاح مع نمو الخطط |
| 2 | الفرض في الواجهة فقط | تجاوز الحدود بطلب API مباشر |
| 3 | فحص ثم إنشاء في خطوتين | حالة سباق تتجاوز الحد |
| 4 | webhook بلا تحقق من التوقيع | خطة مدفوعة مجانًا لأي شخص |
| 5 | معالجة webhook غير idempotent | فوترة مزدوجة أو حالة خاطئة |
| 6 | تجاهل ترتيب الأحداث | إلغاء اشتراك عميل دافع |
| 7 | الاعتماد على إعادة التوجيه كتأكيد دفع | دفع ناجح بحساب غير مفعّل |
| 8 | حذف بيانات عند تراجع الخطة | فقد لا رجعة فيه + مسؤولية قانونية |
| 9 | قطع الخدمة فورًا عند فشل دفع | خسارة عميل بسبب بطاقة منتهية |
| 10 | `float` للمبالغ | أخطاء تقريب في المال |
| 11 | مفتاح ميزة ناقص في خطة | سلوك غير معرَّف |
| 12 | تخزين بيانات بطاقة | مخاطرة PCI هائلة بلا داعٍ |
| 13 | بلا آلية تجاوز للمستأجر | تعديل يدوي خطر في قاعدة البيانات |

## 8. الاختبارات المطلوبة

**`BE-070` (MUST):** اختبار لكل `feature_key` في كل خطة: القيمة معرَّفة ومطبَّقة صحيحًا.

**`BE-071` (MUST):** اختبار حالة السباق: طلبان متزامنان لإنشاء مورد عند الحد → واحد فقط ينجح.

**`BE-072` (MUST):** اختبار توقيع الـ webhook: توقيع خاطئ أو مفقود → رفض بلا أي تغيير في الحالة.

**`BE-073` (MUST):** اختبار idempotency: نفس الحدث مرتين → تغيير واحد فقط.

**`BE-074` (MUST):** اختبار الترتيب: حدث قديم يصل بعد حدث أحدث → **لا يتراجع** عن الحالة الأحدث.

**`BE-075` (MUST):** اختبار تراجع الخطة: البيانات الزائدة عن الحد **لا تُحذف**، والقيود تُطبَّق على الإنشاء الجديد فقط.

**`BE-076` (MUST):** اختبار مهلة السماح: فشل تجديد → الموقع يظل يعمل خلال المهلة.

**`BE-077` (MUST):** اختبار الحسابات المالية: الضريبة والخصم والتناسب الزمني بحساب صحيح بلا أخطاء تقريب.

## 9. Definition of Done — Billing & Entitlements

- [ ] كل فحص ميزة عبر `EntitlementService` — لا فحص اسم خطة في الكود.
- [ ] `feature_key` جديد معرَّف في كل الخطط.
- [ ] الفرض server-side عند نقطة التنفيذ.
- [ ] فحص الحدود ذرّي مع الإنشاء.
- [ ] الخطأ يحمل المفتاح والحد والاستخدام الحالي.
- [ ] التحقق من توقيع الـ webhook قبل أي معالجة.
- [ ] المعالجة idempotent ومحصَّنة ضد ترتيب الوصول.
- [ ] كل حدث مسجَّل بمعرّفه وحالة معالجته.
- [ ] فشل webhook الدفع يُطلق تنبيهًا فوريًا.
- [ ] مهلة سماح مطبَّقة قبل أي تقييد.
- [ ] لا حذف بيانات عند التراجع أو الإلغاء.
- [ ] الاستخدام مقاس عندنا ومعروض للمستخدم مع تنبيه مبكر.
- [ ] كل المبالغ أعداد صحيحة بأصغر وحدة.
- [ ] لا بيانات بطاقة مخزَّنة عندنا.
- [ ] آلية تجاوز على مستوى المستأجر متاحة.
- [ ] كل تغييرات الاشتراك في `audit_logs`.

## 10. ما يحتاج ADR

- تغيير مزوّد الدفع.
- اعتماد فوترة بالاستخدام (usage-based).
- دعم عملات متعددة أو أسعار إقليمية.
- تغيير نموذج الـ entitlements جوهريًا.
- السماح بأي تخزين لبيانات دفع عندنا.
