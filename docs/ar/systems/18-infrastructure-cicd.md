## 1. طوبولوجيا الـ MVP

```
Cloudflare  (DNS · CDN · WAF · TLS · Cloudflare for SaaS)
        │
        ├── Dashboard (Next.js)
        ├── Public Renderer (Next.js)
        └── API (NestJS)
                │
      ┌─────────┼───────────┐
      │         │           │
 PostgreSQL   Redis    Object Storage (R2)
      │         │
      │      Workers (BullMQ)
      │
 نسخ احتياطية مُدارة
```

**`IN-001` (MUST NOT):** **لا container ولا VM لكل مستأجر** (`CORE-012`). الموارد مشتركة مع حدود عادلة.

**`IN-002` (MUST):** كل خدمة تُبنى كـ container قابل للنشر، بلا حالة محلية دائمة (stateless).

> **لماذا:** الخدمة عديمة الحالة يمكن إعادة تشغيلها أو استنساخها أو نقلها بلا فقد شيء — وهذا شرط التوسع الأفقي لاحقًا.

**`IN-003` (MUST):** فصل عمليات الـ API عن الـ workers. **ممنوع** تشغيل وظائف الخلفية داخل عملية الـ API.

> **لماذا:** وظيفة ثقيلة تلتهم الذاكرة تُسقط استجابة الـ API لكل المستخدمين. الفصل يحصر الضرر.

**`IN-004` (MUST):** كل خدمة تعرض `/health` (حية) و`/ready` (جاهزة للاستقبال) بمعنيين مختلفين فعليًا. هذان مسارا فحص للبنية التشغيلية وليسا Product/Business APIs؛ يظلان دون إصدار، ويُستثنيان صراحة من بادئة `/api/v1/` وفق `API-010`. لا يضيف هذا الاستثناء أي endpoint آخر.

**`IN-005` (MUST):** إيقاف لطيف (graceful shutdown): إنهاء الطلبات الجارية والوظائف الحالية قبل الخروج، بمهلة محددة.

## 2. التهيئة والأسرار

**`IN-010` (MUST):** تهيئة بنمط **12-factor**: كل شيء من متغيرات البيئة.

**`IN-011` (MUST):** التحقق من التهيئة بـ schema **عند الإقلاع**، والفشل الصريح الفوري عند نقص مطلوب (`CORE-071`).

> **لماذا:** خدمة تقلع بإعداد ناقص تنهار لاحقًا في منتصف عملية مستخدم — وقتها يكون التشخيص أصعب بكثير من فشل واضح عند الإقلاع.

**`IN-012` (MUST):** فصل كامل للأسرار بين `local` / `staging` / `production`. **ممنوع** أي مشاركة.

**`IN-013` (MUST):** `.env.example` محدَّث دائمًا (`CORE-072`).

**`IN-014` (MUST NOT):** ممنوع بيانات اعتماد الإنتاج على أجهزة المطورين (`SE-044`).

**`IN-015` (MUST):** تدوير الأسرار ممكن **بلا توقف خدمة** (دعم مفتاحين صالحين أثناء الانتقال).

---

## 3. البيئات

```
Local → CI → Preview → Staging → Production
```

**`IN-020` (MUST):** `staging` **مطابق بنيويًا** للإنتاج (نفس الخدمات والإصدارات)، وإن اختلف الحجم.

**`IN-021` (MUST NOT):** **ممنوع** بيانات إنتاج حقيقية في أي بيئة غير الإنتاج.

> **لماذا:** بيانات عملاء في staging تعني سطح تسريب إضافيًا ببيئة أقل حماية — والتزامًا قانونيًا لا نريده.

**`IN-022` (MUST):** بيانات الاختبار مولَّدة أو مُخفاة الهوية (anonymized) بشكل لا رجعة فيه.

**`IN-023` (MUST):** بيئات المعاينة (preview) لكل PR **معزولة** ولا تلمس بيانات الإنتاج إطلاقًا.

## 4. خط الـ CI

**`IN-030` (MUST):** يعمل على كل PR، وكلها **إلزامية** قبل الدمج:

> **انطباق Stage 00:** اختبارات cross-tenant وقت التشغيل فقط هي N/A ما دام لا يوجد سطح Domain قادر على التعامل مع المستأجرين، وفق [ADR-001](../../adr/ADR-001-stage-00-cross-tenant-test-applicability.md). تظل الفحوص الأخرى المنطبقة إلزامية. تُسجّل N/A صراحة، ولا تُعرض كاختبار ناجح أو اختبار وهمي تم تخطيه. أول كود قادر على التعامل مع المستأجرين في Stage 01 يجب أن يصاحبه الاختبار.

```
1. تثبيت بـ --frozen-lockfile
2. Lint
3. tsc --noEmit  (فحص الأنواع)
4. اختبارات الوحدة
5. اختبارات التكامل
6. مجموعة اختبارات الأمن (بما فيها cross-tenant)   ← حرجة
7. فحص الأسرار
8. فحص ثغرات الاعتماديات
9. فحص حدود الموديولات + الاعتماد الدائري
10. البناء
11. ميزانية حجم الحزم
12. اختبارات الوصولية
13. الانحدار البصري (RTL + LTR)
```

> **أدلة الاعتماديات لـ`IN-030`:** تُحفظ inventory الكاملة لـDirect/Transitive وgraph diff، وتصنيف التنفيذ/الشحن، ونتائج مراجعة الثغرات والترخيص وintegrity/source المؤرخة، واستثناءات direct-age عند لزومها، وdispositions للـfindings مع owner والموافقة ومواعيد tracking السارية وإعادة التقييم عند الأحداث وفق [CORE-002](../00-PROJECT-RULES.md). تُشمل مسارات dev/test وoptional/platform؛ غياب دليل مطلوب أو قبول منتهٍ/غير منطبق يمنع الدمج. تبقى جميع hard blockers وبوابة High/Critical دون تغيير. لا يلغي متطلب الأدلة هذا أي فحص CI.

**`IN-031` (MUST NOT):** **ممنوع الدمج مع CI أحمر** (`CORE-046`).

**`IN-032` (MUST):** الاختبارات المتقطعة (flaky) تُصلَح أو تُعزل **فورًا**.

> **لماذا:** اختبار متقطع واحد يعلّم الفريق تجاهل اللون الأحمر — وبعدها لن يلاحظ أحد العطل الحقيقي.

**`IN-033` (MUST):** زمن الـ CI معقول (**< 15 دقيقة** للمسار الكامل). الأبطأ من ذلك يُوازى أو يُقسَّم.

**`IN-034` (MUST):** الـ CI يبني **مرة واحدة** ويرقّي نفس القطعة (artifact) عبر البيئات. ممنوع إعادة البناء لكل بيئة.

> **لماذا:** إعادة البناء تعني أن ما اختُبر في staging ليس بالضبط ما نُشر في الإنتاج.

## 5. النشر

**`IN-040` (MUST):** النشر **آلي** من `main` بعد نجاح كل الفحوص.

**`IN-041` (MUST):** النشر **قابل للرجوع** بأمر واحد وبسرعة.

**`IN-042` (MUST):** نشر تدريجي (rolling) بلا توقف، مع فحوص الجاهزية.

**`IN-043` (MUST):** الـ migrations تُطبَّق **قبل** نشر الكود الذي يحتاجها، وتكون متوافقة مع الإصدار السابق (`DM-033`).

> **لماذا:** أثناء النشر التدريجي يعمل الإصداران معًا لدقائق. migration غير متوافقة خلفيًا تكسر النسخ القديمة التي ما زالت تخدم مستخدمين.

**`IN-044` (MUST):** الميزات عالية المخاطر خلف feature flags (`CORE-050`).

**`IN-045` (MUST):** بعد كل نشر: **فحص فعلي للـ observability** (معدل الأخطاء، الكمون، عمق الطوابير) قبل اعتباره ناجحًا.

**`IN-046` (MUST):** خطة الرجوع مكتوبة في كل PR (`CORE-043`).

**`IN-047` (MUST NOT):** **ممنوع** النشر اليدوي إلى الإنتاج بلا سجل. كل نشر مؤتمت ومسجَّل.

---

## 6. البنية التحتية ككود

**`IN-050` (MUST):** بعد استقرار الـ MVP، تهيئة البنية التحتية **ككود** في `/infra` تحت مراجعة Git.

**`IN-051` (MUST NOT):** ممنوع تغيير يدوي في الإنتاج بلا تسجيل. التغيير اليدوي غير المسجَّل يجعل إعادة بناء البيئة مستحيلة عند الكارثة.

**`IN-052` (MUST):** حدود موارد صريحة (CPU/ذاكرة) لكل خدمة، خصوصًا الـ workers.

**`IN-053` (MUST):** حجم مجمّع اتصالات قاعدة البيانات (pool) محسوب ومحدود لكل خدمة، بحيث لا يستنزف مجموع الخدمات حد الاتصالات.

> **لماذا:** استنزاف الاتصالات يعني توقف كل شيء دفعة واحدة — وهو من أشهر أسباب الأعطال الكاملة في هذه المعمارية.

## 7. الأنماط الممنوعة

| # | النمط | لماذا هو خطر |
|---|---|---|
| 1 | container لكل مستأجر | تكلفة تنمو خطيًا — لا يتوسع |
| 2 | workers داخل عملية الـ API | وظيفة ثقيلة تُسقط الـ API للجميع |
| 3 | حالة محلية في الخدمة | يمنع التوسع الأفقي |
| 4 | تهيئة بلا تحقق عند الإقلاع | انهيار لاحق أصعب تشخيصًا |
| 5 | بيانات إنتاج في staging | سطح تسريب + التزام قانوني |
| 6 | الدمج مع CI أحمر | كسر متراكم في `main` |
| 7 | تجاهل الاختبارات المتقطعة | الفريق يتجاهل الأحمر كله |
| 8 | إعادة البناء لكل بيئة | المنشور ليس المختبَر |
| 9 | migration غير متوافقة خلفيًا | كسر أثناء النشر التدريجي |
| 10 | نشر يدوي غير مسجَّل | لا أحد يعرف ما يعمل في الإنتاج |
| 11 | بلا حدود موارد | خدمة واحدة تجوّع البقية |
| 12 | pool غير محدود | استنزاف اتصالات = عطل كامل |
| 13 | تغيير يدوي في الإنتاج | استحالة إعادة البناء عند الكارثة |
| 14 | أسرار مشتركة بين البيئات | اختراق staging = اختراق الإنتاج |

## 8. Definition of Done — Infrastructure & CI/CD

- [ ] الخدمة عديمة الحالة وقابلة للنشر كـ container.
- [ ] `/health` و `/ready` مطبَّقان بمعنيين مختلفين.
- [ ] إيقاف لطيف بمهلة محددة.
- [ ] التهيئة متحقَّق منها عند الإقلاع، والفشل صريح.
- [ ] `.env.example` محدَّث.
- [ ] الأسرار مفصولة بين البيئات وقابلة للتدوير بلا توقف.
- [ ] كل فحوص الـ CI الثلاثة عشر خضراء.
- [ ] لا اختبارات متقطعة.
- [ ] بناء واحد يُرقَّى عبر البيئات.
- [ ] الـ migration متوافقة خلفيًا ومطبَّقة قبل الكود.
- [ ] الميزة عالية المخاطر خلف flag.
- [ ] النشر قابل للرجوع، والخطة مكتوبة في الـ PR.
- [ ] فحص observability بعد النشر.
- [ ] حدود موارد و pool محسوبة.
- [ ] لا بيانات إنتاج خارج الإنتاج.

---

## 9. ما يحتاج ADR

- تغيير مزوّد الاستضافة أو الـ CDN.
- الانتقال إلى Kubernetes أو منصة تنسيق.
- إضافة منطقة جغرافية ثانية.
- تغيير استراتيجية النشر.
- إضافة بيئة دائمة جديدة.
