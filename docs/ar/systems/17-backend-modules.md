# 17 — Backend Module Boundaries

> **بادئة القواعد:** `BM-` · **الحالة:** إلزامي · **المالك:** Backend
> **المرجع الأعلى:** [`../../en/00-PROJECT-RULES.md`](../../en/00-PROJECT-RULES.md) · **نسخة النظام الحاكمة:** [`../../en/systems/17-backend-modules.md`](../../en/systems/17-backend-modules.md) · هذه ترجمة عربية متزامنة.
> **يحقق المبدأ:** `CORE-013` (Modular Monolith first)

---

## 0. الفكرة الحاكمة

**Modular Monolith = بساطة نشر الـ monolith + انضباط حدود الـ microservices.**

نبدأ بتطبيق backend واحد منظَّم إلى موديولات ذات حدود صارمة. الهدف أن يصبح فصل أي موديول لاحقًا **عملية ميكانيكية**، لا إعادة كتابة.

> **لماذا لا microservices من البداية:** فريق صغير ومنتج لم يثبت بعد + microservices = تعقيد تشغيلي هائل (شبكة، اتساق موزع، تتبع، نشر متعدد) مقابل فائدة صفرية في هذه المرحلة. الثمن يُدفع فورًا والعائد قد لا يأتي أبدًا.

> **لماذا الحدود من البداية:** لأن monolith بلا حدود يتحول خلال عام إلى «كرة طين» — كل شيء يستورد كل شيء، ولا يمكن فصل أو اختبار أو فهم أي جزء منفردًا. **الحدود أرخص شيء تفعله اليوم، وأغلى شيء تضيفه لاحقًا.**

## 1. الموديولات

```
/apps/api/src/modules
  /auth              المصادقة والجلسات
  /users             هوية المستخدم
  /organizations     المستأجرون والعضويات والأدوار
  /websites          دورة حياة الموقع
  /pages             الصفحات
  /sections          كتل المحتوى
  /templates         القوالب والـ blueprints
  /themes            قيم التصميم
  /revisions         نسخ draft/published والنشر
  /assets            الملفات والوسائط
  /domains           الدومينات و TLS
  /forms             تعريف النماذج
  /leads             إرسالات النماذج
  /billing           الاشتراكات والدفع
  /entitlements      الميزات والحدود
  /analytics         الأحداث والتجميعات
  /ai                التوليد وعزل المزوّد
  /notifications     البريد والـ webhooks
  /audit             سجل التدقيق
```

**`BM-001` (MUST):** كل موديول له **مالك واضح ومسؤولية واحدة**. الموديول الذي لا تستطيع وصف مسؤوليته في جملة واحدة يحتاج تقسيمًا.

---

## 2. بنية الموديول

**`BM-010` (MUST):** البنية الداخلية الموحّدة:

```
/modules/websites
  index.ts                   ← الواجهة العامة — الشيء الوحيد المسموح استيراده
  websites.service.ts        ← منطق الأعمال
  websites.controller.ts     ← طبقة HTTP
  websites.repository.ts     ← الوصول للبيانات
  websites.events.ts         ← الأحداث المنشورة
  /dto                       ← عقود الدخول والخروج
  /internal                  ← تفاصيل خاصة — ممنوع الاستيراد من الخارج
```

**`BM-011` (MUST):** `index.ts` يصدّر **فقط**: واجهة الخدمة العامة، الأنواع العامة، وتعريفات الأحداث. **لا مستودعات، لا كيانات داخلية، لا دوال مساعدة.**

```ts
// modules/websites/index.ts
export type { WebsiteSummary, WebsiteDetail } from './dto';
export { WebsitesService } from './websites.service';
export type { WebsitePublished, WebsiteDeleted } from './websites.events';
// ممنوع: export { WebsitesRepository }
```

## 3. قواعد الحدود

**`BM-020` (MUST NOT):** **ممنوع** الاستيراد من المسارات الداخلية لموديول آخر (`CORE-023`):

```ts
// ❌ ممنوع
import { WebsitesRepository } from '../websites/websites.repository';
import { normalizeSlug } from '../websites/internal/slug-utils';

// ✅ صحيح
import { WebsitesService } from '../websites';
```

**`BM-021` (MUST):** هذه القاعدة **مفروضة آليًا** بقاعدة lint أو أداة حدود، لا بالانضباط البشري وحده.

> **لماذا:** القاعدة غير المفروضة آليًا تُخترق في أول ليلة تسليم تحت ضغط. الفرض الآلي يجعل المخالفة مستحيلة لا مجرد ممنوعة.

**`BM-022` (MUST NOT):** **ممنوع** أن يستعلم موديول عن جداول موديول آخر مباشرةً.

> **لماذا:** هذا أخطر أشكال التشابك وأصعبها اكتشافًا. يجعل تغيير أي schema يكسر موديولات لا علاقة ظاهرة لها به، ويجعل فصل الموديول لاحقًا مستحيلًا.

**`BM-023` (MUST):** كل موديول يملك جداوله. جدول له مالك واحد فقط.

**`BM-024` (MUST):** الوصول لبيانات موديول آخر عبر **واجهته العامة فقط**.

---

## 4. التواصل بين الموديولات

**`BM-030` (MUST):** أسلوبان مسموحان فقط:

| الأسلوب | متى | مثال |
|---|---|---|
| **استدعاء واجهة عامة** | تحتاج إجابة الآن للاستمرار | `entitlements.can(ctx, 'custom_domain')` |
| **حدث نطاق (domain event)** | تُعلم غيرك بما حدث، ولا تنتظر | `WebsitePublished` |

**`BM-031` (MUST):** الأحداث `PascalCase` بصيغة الماضي، وتحمل معرّفات لا كائنات كاملة:

```ts
type WebsitePublished = {
  websiteId: string;
  organizationId: string;
  revisionId: string;
  publishedAt: string;
};
```

**`BM-032` (MUST):** ناشر الحدث **لا يعرف مشتركيه**. إضافة مشترك جديد لا تتطلب تعديل الناشر.

**`BM-033` (MUST):** فشل مشترك **لا يُفشل** العملية الأصلية ولا بقية المشتركين.

> **لماذا:** فشل إرسال بريد تهنئة يجب ألا يُفشل عملية نشر ناجحة.

**`BM-034` (MUST NOT):** **ممنوع الاعتماد الدائري بين الموديولات.** الدورة تعني أن الاثنين موديول واحد في الحقيقة، أو أن هناك موديولًا ثالثًا مفقودًا.

**`BM-035` (MUST):** الدورة تُحل بواحد من ثلاثة: عكس الاتجاه بحدث · استخراج المشترك لموديول ثالث · إعادة النظر في الحدود.

**`BM-036` (MUST):** فحص الدورات **آلي في CI**.

---

## 5. الاتساق والمعاملات

**`BM-040` (MUST):** المعاملة (transaction) **داخل موديول واحد**. ممنوع معاملة تمتد عبر موديولات.

> **لماذا:** المعاملة العابرة تربط الموديولات ربطًا لا ينفصل، وتجعل فصل أي منها لاحقًا مستحيلًا.

**`BM-041` (MUST):** ما يحتاج اتساقًا فوريًا **يجب أن يكون في موديول واحد**. لو لم يكن كذلك، فالحدود مرسومة خطأ.

**`BM-042` (MUST):** الاتساق بين الموديولات **نهائي (eventual)** عبر الأحداث، مع تعويض عند الفشل.

**`BM-043` (MUST):** معالجة الأحداث idempotent (`QJ-030`).

---

## 6. الموديولات المشتركة

**`BM-050` (MUST):** `entitlements` و `audit` و `notifications` موديولات **أفقية** تستدعيها كثير من الموديولات — وهذا مقبول ومقصود.

**`BM-051` (MUST):** الموديول الأفقي **لا يستدعي** الموديولات الرأسية. `entitlements` لا يعرف `websites`.

> **لماذا:** بلا هذه القاعدة تنشأ دورات فورًا، ويصبح الموديول الأفقي عقدة يمر بها كل شيء.

**`BM-052` (MUST):** الكود المشترك العام (أدوات، أنواع، مساعدات) في `packages/`، لا في موديول يستورده الجميع.

---

## 7. متى نفصل موديولًا لخدمة

**`BM-060` (MUST NOT):** **ممنوع** الفصل بلا ADR معتمد يحمل **قياسات فعلية** (`CORE-013`).

**`BM-061` (MUST):** المبررات المقبولة — بقياس لا بتوقع:

| المبرر | القياس المطلوب |
|---|---|
| ضغط موارد مختلف جذريًا | استهلاك CPU/ذاكرة مقاس يعطّل البقية |
| اعتمادية مختلفة | فشله يُسقط ما لا يجب أن يسقط (blast radius) |
| تشابك النشر | نشره المتكرر يعطّل فرقًا أخرى بشكل مقاس |
| ملكية فريق منفصل | فريق مستقل فعلًا بدورة إصدار مختلفة |
| تقنية مختلفة ضرورية | حاجة حقيقية لا تفضيل |

**`BM-062` (MUST NOT):** مبررات **مرفوضة**: «الـ monolith سيئ» · «microservices أحدث» · «قد نحتاج التوسع يومًا» · «هكذا تفعل الشركات الكبيرة».

**`BM-063` (MUST):** الموديول المرشَّح للفصل يجب أن يكون **نظيف الحدود أصلًا**. لو لم يكن كذلك، نظّف حدوده أولًا — وغالبًا يختفي سبب الفصل بعد التنظيف.

## 8. الأنماط الممنوعة

| # | النمط | لماذا هو خطر |
|---|---|---|
| 1 | استيراد المسارات الداخلية | تشابك يمنع الفصل والاختبار |
| 2 | الاستعلام عن جداول موديول آخر | أخطر تشابك وأصعبه اكتشافًا |
| 3 | اعتماد دائري | حدود مرسومة خطأ |
| 4 | معاملة عابرة للموديولات | ربط لا ينفصل |
| 5 | حدث يحمل كائنات كاملة | بيانات قديمة + حمولة ضخمة |
| 6 | فشل مشترك يفشل العملية | عطل من أثر جانبي |
| 7 | موديول أفقي يستدعي رأسيًا | دورات فورية |
| 8 | موديول «utils» يستورده الجميع | كرة طين متنكرة |
| 9 | موديول بلا مالك | لا أحد يحرس حدوده |
| 10 | فصل خدمة بلا قياس | تعقيد هائل بلا عائد |
| 11 | حدود بلا فرض آلي | تُخترق في أول ليلة ضغط |

## 9. الاختبارات المطلوبة

**`BM-070` (MUST):** فحص آلي في CI يمنع الاستيراد من المسارات الداخلية.

**`BM-071` (MUST):** فحص آلي للاعتماد الدائري.

**`BM-072` (MUST):** اختبار وحدة لكل موديول **مع محاكاة (mock) للموديولات الأخرى** عبر واجهاتها العامة — دليل عملي على سلامة الحدود.

**`BM-073` (MUST):** اختبار الأحداث: الناشر يطلق الحدث الصحيح؛ المشترك يعالجه بشكل idempotent؛ فشل المشترك لا يؤثر على الناشر.

**`BM-074` (MUST):** فحص ملكية الجداول: كل جدول يُقرأ ويُكتب من موديول واحد فقط.

---

## 10. Definition of Done — Module Boundaries

- [ ] الكود الجديد في الموديول المالك الصحيح.
- [ ] لا استيراد من مسارات داخلية لموديول آخر.
- [ ] لا استعلام مباشر عن جداول موديول آخر.
- [ ] `index.ts` يصدّر الواجهة العامة فقط.
- [ ] لا اعتماد دائري (الفحص الآلي أخضر).
- [ ] المعاملات داخل موديول واحد.
- [ ] الأحداث `PascalCase` ماضية وتحمل معرّفات.
- [ ] معالجة الأحداث idempotent، وفشلها لا يفشل الناشر.
- [ ] الموديول الأفقي لا يستدعي رأسيًا.
- [ ] اختبارات الوحدة تحاكي الموديولات الأخرى عبر واجهاتها.
- [ ] ملكية الجداول واضحة ومحفوظة.

---

## 11. ما يحتاج ADR

- فصل أي موديول إلى خدمة مستقلة.
- إضافة موديول جديد كبير (وإعادة رسم الحدود).
- السماح باستعلام عابر للموديولات.
- إضافة ناقل أحداث خارجي.
- دمج موديولين أو تفكيك موديول قائم.
