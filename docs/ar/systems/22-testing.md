# 22 — Testing Strategy

> **بادئة القواعد:** `TS-` · **الحالة:** إلزامي · **المالك:** QA / الجميع
> **المرجع الأعلى:** [`../../en/00-PROJECT-RULES.md`](../../en/00-PROJECT-RULES.md) · **نسخة النظام الحاكمة:** [`../../en/systems/22-testing.md`](../../en/systems/22-testing.md) · هذه ترجمة عربية متزامنة.

## 0. الفلسفة

الاختبارات ليست واجبًا بيروقراطيًا. هي **الشيء الوحيد** الذي يسمح بتعديل نظام متعدد المستأجرين بثقة بعد سنة من بنائه — حين لا يتذكر أحد لماذا كُتب هذا السطر.

**الأولوية ليست تغطية عالية بالنسبة المئوية، بل تغطية عالية لما يقتل.** اختبار يغطي دالة تنسيق تواريخ لا يساوي شيئًا أمام اختبار يمنع مستأجرًا من قراءة بيانات مستأجر آخر.

## 1. الهرم

```
        ┌──────────┐
        │   E2E    │  قليلة · بطيئة · تغطي الرحلات الحرجة فقط
        ├──────────┤
        │Integration│ متوسطة · قاعدة بيانات حقيقية · حدود الموديولات
        ├──────────┤
        │   Unit    │ كثيرة · سريعة · منطق الأعمال الخالص
        └──────────┘
    ──────────────────────
     أمن · عزل · عقود  ← تقطع الهرم كله عرضيًا
```

## 2. أنواع الاختبارات

**`TS-001` (MUST):** التغطية المطلوبة لكل نوع:

| النوع | ما يغطيه |
|---|---|
| **Unit** | قواعد النطاق · منطق الـ entitlements · تحويلات الـ schema · الحسابات المالية |
| **Integration** | المستودعات · حراس المصادقة · تدفق النشر · webhooks الفوترة · الطوابير |
| **Contract** | schemas مخرجات الـ AI · الـ webhooks · محوّلات المزوّدين · عقود الـ API |
| **E2E** | تسجيل → توليد → تعديل → نشر → زيارة الموقع العام |
| **Security** | الوصول العابر للمستأجرين · XSS · التحقق من الرفع · التفويض · SSRF · حقن الـ prompt |
| **Performance** | مسار الرندر الساخن · دفعات النشر · استيعاب الـ analytics |
| **Visual regression** | variants الأقسام عبر نقاط التوقف و RTL/LTR |
| **Accessibility** | الشاشات الرئيسية وكل variant |

## 3. الاختبار الإلزامي الأول

> ### `TS-010` (MUST) — الاختبار الأهم في النظام كله
> **يجب وجود اختبار آلي يحاول الوصول إلى Site/Lead/Asset لمستأجر آخر ويتأكد من الرفض.**
> هذا الاختبار **لا يُتخطى، ولا يُعطَّل، ولا يُؤجَّل** تحت أي ضغط تسليم.

**`TS-011` (MUST):** مجموعة `cross-tenant.spec.ts` تعمل في CI وتفشل الـ build عند أي كسر (`MT-060`).

> **انطباق `TS-010` / `TS-011` في Stage 00:** اختبارات cross-tenant وقت التشغيل هي N/A ما دام لا يوجد سطح Domain قادر على التعامل مع المستأجرين، وفق [ADR-001](../../adr/ADR-001-stage-00-cross-tenant-test-applicability.md). عزل المستأجرين يظل إلزاميًا من اليوم الأول. يُمنع إنشاء Tenant وهمي أو Authentication مبكر أو اختبارات نجاح وهمية أو تخطٍ صامت. أول كود قادر على التعامل مع المستأجرين في Stage 01 يجب أن يصاحبه الاختبار؛ لا يُدمج أي مورد Tenant-scoped في Stage 01 أو بعدها دون اختبارات cross-tenant سلبية. هذا ليس إعفاء دائمًا ولا يشمل أي فئة اختبارات أخرى.

**`TS-012` (MUST):** التغطية لكل الأفعال: قراءة · قائمة · إنشاء · تعديل · حذف · رفع (`MT-062`).

**`TS-013` (MUST):** أي جدول جديد مملوك لمستأجر **لا يُدمج** قبل إضافة اختباراته (`MT-064`).

## 4. قواعد كتابة الاختبارات

**`TS-020` (MUST):** الاختبار **مستقل**: لا يعتمد على ترتيب التنفيذ ولا على حالة خلّفها اختبار آخر.

**`TS-021` (MUST):** الاختبار **حتمي**. المتقطع يُصلَح أو يُعزل فورًا (`IN-032`).

> **لماذا:** اختبار متقطع واحد يعلّم الفريق تجاهل الأحمر. بعدها لن يلاحظ أحد العطل الحقيقي.

**`TS-022` (MUST):** الاختبار يصف **السلوك لا التنفيذ**:

```ts
// ❌ يكسر مع كل إعادة هيكلة
it('calls websitesRepository.findById once')

// ✅ يبقى صحيحًا ما بقي السلوك صحيحًا
it('returns 404 when the website belongs to another tenant')
```

**`TS-023` (MUST):** التسمية تشرح **المتوقع**، ليقرأ المطور الفشل ويفهم المشكلة بلا فتح الكود.

**`TS-024` (MUST):** اختبارات التكامل على **قاعدة بيانات حقيقية** (حاوية اختبار)، لا محاكاة لقاعدة البيانات.

> **لماذا:** محاكاة قاعدة البيانات تخفي بالضبط ما نريد اختباره: القيود، والفهارس، وسلوك المعاملات، وحالات السباق.

**`TS-025` (MUST):** لكل باق يُكتشف في الإنتاج: **اختبار يعيد إنتاجه أولًا**، ثم الإصلاح.

> **لماذا:** بلا ذلك لا دليل أن الإصلاح صحيح، ولا حماية من عودة الباق بعد ستة أشهر.

**`TS-026` (MUST NOT):** ممنوع تعطيل اختبار (`skip`) بلا تذكرة مرتبطة وتاريخ. الاختبارات المعطَّلة تتراكم ثم تُنسى.

**`TS-027` (MUST):** المعطيات (fixtures) تُنشئ بيانات **واقعية**: عربي وإنجليزي · نصوص طويلة وقصيرة · حقول اختيارية غائبة · محارف خاصة.

---

## 5. ما يجب اختباره دائمًا

**`TS-030` (MUST):** لا يُدمج PR بلا اختبار عند لمس أي من:

- منطق يعتمد على المستأجر (أي منطق)
- التفويض أو الأدوار
- الـ entitlements أو الحدود
- الفوترة أو أي حساب مالي
- تدفق النشر
- تحقق الـ schema
- التحقق من الملفات
- التحقق من الدومينات
- تدفق المصادقة

**`TS-031` (MUST):** الحالات الحدية إلزامية، لا اختيارية:

| الفئة | أمثلة |
|---|---|
| **الفراغ** | قائمة فارغة · موقع بلا صفحات · قسم بأقل بيانات |
| **الحدود** | عند الحد · عند الحد ناقص واحد · عند الحد زائد واحد |
| **التزامن** | طلبان متزامنان على نفس المورد |
| **الفشل** | الشبكة · الطرف الثالث · قاعدة البيانات · الـ cache |
| **الخبيث** | XSS · SQL · SSRF · اجتياز مسار · حقن prompt |
| **التدويل** | عربي · إنجليزي · RTL · LTR · محارف مختلطة |

## 6. اختبارات الـ E2E

**`TS-040` (MUST):** الرحلة الكاملة مغطاة **كاختبار واحد على الأقل**:

```
تسجيل → إنشاء موقع → توليد AI → تعديل نص → رفع صورة
      → تغيير variant → إعادة ترتيب → نشر → زيارة الموقع العام
      → التأكد من ظهور التعديلات
```

**`TS-041` (MUST):** رحلة **عدم التسرب**: تعديل بلا نشر → الموقع العام **لا** يعكسه (`RP-060`).

**`TS-042` (MUST):** رحلة الدومين المخصص من الإضافة للتفعيل (بـ DNS محاكى).

**`TS-043` (MUST):** رحلة الـ lead: زائر يرسل نموذجًا → يظهر في لوحة التحكم → يُرسل الإشعار.

**`TS-044` (MUST):** الـ E2E **قليلة ومركزة**. تغطية كل حالة حدية عبر E2E تنتج مجموعة بطيئة هشة يتجاهلها الفريق.

---

## 7. الأداء والانحدار البصري

**`TS-050` (MUST):** اختبار عدد الاستعلامات لرندر الصفحة (`PF-070`).

**`TS-051` (MUST):** اختبار حمل للمسارات الحرجة قبل الإطلاق (`PF-062`).

**`TS-052` (MUST):** انحدار بصري لكل variant عبر: RTL/LTR × موبايل/ديسكتوب (`CE-072`).

**`TS-053` (MUST):** اختبار وصولية آلي على كل شاشة رئيسية (`FE-091`).

## 8. الأنماط الممنوعة

| # | النمط | لماذا هو خطر |
|---|---|---|
| 1 | لا اختبارات cross-tenant | أخطر ثغرة تمر بلا اكتشاف |
| 2 | تجاهل الاختبارات المتقطعة | الفريق يتجاهل الأحمر كله |
| 3 | اختبار تفاصيل التنفيذ | يكسر مع كل إعادة هيكلة |
| 4 | محاكاة قاعدة البيانات في التكامل | يخفي القيود والسباقات |
| 5 | اختبارات متسلسلة الاعتماد | فشل غامض وترتيب هش |
| 6 | `skip` بلا تذكرة | تراكم صامت ثم نسيان |
| 7 | إصلاح باق بلا اختبار يعيد إنتاجه | يعود بعد ستة أشهر |
| 8 | تغطية الحالة السعيدة فقط | الإنتاج كله حالات حدية |
| 9 | معطيات إنجليزية فقط | كسر RTL يُكتشف عند العميل |
| 10 | E2E لكل شيء | مجموعة بطيئة هشة مُهمَلة |
| 11 | ملاحقة نسبة التغطية | اختبارات بلا قيمة |
| 12 | تعطيل اختبارات الأمن للتسليم | بالضبط ما لا يجب تعطيله |

## 9. المتطلبات في CI

**`TS-060` (MUST):** كل الاختبارات تعمل على كل PR، وكلها إلزامية للدمج (`IN-030`).

**`TS-061` (MUST):** مجموعة الأمن (بما فيها cross-tenant) **لا تُتخطى أبدًا** — ولا حتى لإصلاح عاجل.

> حالة N/A الخاصة باختبارات cross-tenant وقت التشغيل في Stage 00 فقط موثقة في [ADR-001](../../adr/ADR-001-stage-00-cross-tenant-test-applicability.md) وملاحظة انطباق `TS-010` / `TS-011` أعلاه. ليست إذنًا بتخطي مجموعة اختبارات الأمن.

**`TS-062` (MUST):** الاختبارات البطيئة موازية للحفاظ على زمن CI < 15 دقيقة (`IN-033`).

**`TS-063` (MUST):** تقرير التغطية منشور، **والانحدار الكبير فيه يُناقَش** — بلا ملاحقة رقم لذاته.

## 10. Definition of Done — Testing

- [ ] اختبارات الوحدة للمنطق الجديد.
- [ ] اختبارات التكامل للمسارات الجديدة على قاعدة بيانات حقيقية.
- [ ] **اختبارات cross-tenant لكل الأفعال** إن لمس التغيير بيانات مستأجر.
- [ ] اختبارات عقد لأي schema أو webhook جديد.
- [ ] الحالات الحدية: فراغ · حدود · تزامن · فشل · خبيث · تدويل.
- [ ] باق مُصلَح مسبوق باختبار يعيد إنتاجه.
- [ ] الاختبارات مستقلة وحتمية.
- [ ] الأسماء تصف السلوك لا التنفيذ.
- [ ] المعطيات تشمل عربي وإنجليزي.
- [ ] انحدار بصري في RTL و LTR إن لمس الواجهة.
- [ ] اختبار وصولية إن لمس الواجهة.
- [ ] اختبار أداء إن لمس مسارًا ساخنًا.
- [ ] لا `skip` بلا تذكرة وتاريخ.
- [ ] كل CI أخضر.

---

## 11. ما يحتاج ADR

- تغيير إطار الاختبارات الأساسي.
- تخطي أي فئة اختبارات في CI.
- خفض متطلبات الاختبار لأي نظام.
- اعتماد اختبار في الإنتاج (testing in production).
