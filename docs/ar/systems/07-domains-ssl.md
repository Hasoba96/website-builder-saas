# 07 — Subdomains / Custom Domains / SSL

> **بادئة القواعد:** `DN-` · **الحالة:** إلزامي · **المالك:** Backend / DevOps
> **المرجع الأعلى:** [`../../en/00-PROJECT-RULES.md`](../../en/00-PROJECT-RULES.md) · **نسخة النظام الحاكمة:** [`../../en/systems/07-domains-ssl.md`](../../en/systems/07-domains-ssl.md) · هذه ترجمة عربية متزامنة.

## 0. الغرض والنطاق

ربط الدومين هو **أكثر جزء في المنتج يولّد تذاكر دعم**، لأنه الجزء الوحيد الذي يعتمد على إعداد يقوم به المستخدم خارج منصتنا (عند مسجّل الدومين). لذلك: **الوضوح والحالات الصريحة والتحقق الخلفي ليست تحسينات — هي المتطلب الأساسي.**

كما أنه سطح هجوم حقيقي: من يربط دومينًا لا يملكه يستولي على حركة مرور ليست له.

---

## 1. Subdomains المنصة

```
*.platform.com  →  Cloudflare (DNS + TLS + WAF)  →  Renderer
```

**`DN-001` (MUST):** Wildcard DNS + wildcard TLS يغطيان كل الـ subdomains. **ممنوع** إنشاء سجل DNS أو شهادة لكل موقع على حدة.

**`DN-002` (MUST):** الـ router يستخرج الـ hostname → يستخرج الـ slug → يتحقق من حالة الموقع → يخدم النسخة المنشورة.

**`DN-003` (MUST):** الـ slug يُتحقق منه عند الإنشاء: حروف وأرقام وشرطات فقط، `3–63` حرفًا، لا يبدأ أو ينتهي بشرطة، وليس في **قائمة الكلمات المحجوزة**.

**`DN-004` (MUST):** قائمة محجوزة إلزامية تشمل على الأقل:

```
www, api, app, admin, dashboard, cdn, assets, static, mail, smtp, imap,
ftp, ns1, ns2, blog, help, support, docs, status, billing, pay, checkout,
login, auth, account, secure, test, staging, dev, preview, internal,
webmail, autodiscover, _domainkey, _dmarc
```

> **لماذا:** slug اسمه `mail` أو `_dmarc` يمكن أن يعطّل بريد المنصة أو يُستخدم في تصيّد يبدو رسميًا.

**`DN-005` (MUST):** تغيير الـ slug يترك **إعادة توجيه دائمة** من القديم لفترة موثَّقة، ويمنع إعادة استخدام القديم خلالها.

> **لماذا:** بلا ذلك، روابط العميل المنشورة تنكسر، وقد يستولي شخص آخر على الـ slug القديم ويستقبل زواره.

## 2. الدومينات المخصصة — التدفق

```
المستخدم يدخل example.com
      ↓
تطبيع الـ hostname + فحص الـ entitlement + فحص التفرد
      ↓
إنشاء سجل بحالة pending_dns  + توليد verification token
      ↓
عرض تعليمات DNS واضحة (CNAME / A / TXT)
      ↓
وظيفة تحقق خلفية (بتراجع أسّي)
      ↓
verifying → تم التحقق من الملكية
      ↓
tls_pending → تجهيز الشهادة
      ↓
active → hostname → site_id في الـ cache
```

**`DN-010` (MUST):** الحالات الصريحة **حصريًا**:

| الحالة | المعنى | ما يراه المستخدم |
|---|---|---|
| `pending_dns` | ننتظر إعداد DNS | تعليمات واضحة + السجلات المطلوبة |
| `verifying` | نتحقق حاليًا | «جارٍ التحقق — قد يستغرق حتى 48 ساعة» |
| `tls_pending` | نجهّز الشهادة | «جارٍ تفعيل الحماية» |
| `active` | يعمل | ✅ + رابط للموقع |
| `failed` | فشل التحقق | **السبب الدقيق** + خطوة التصحيح |
| `disconnected` | كان يعمل ثم انقطع | تنبيه + سبب + خطوة الإصلاح |

**`DN-011` (MUST):** حالة `failed` **يجب** أن تحمل سببًا قابلًا للتصرف: «سجل CNAME غير موجود» · «يشير إلى `x.y.z` بدلًا من `target.platform.com`» · «الدومين مربوط بحساب آخر». **ممنوع** «فشل التحقق» وحدها.

**`DN-012` (MUST):** التحقق **خلفي دوري**، لا استطلاع متزامن من المتصفح.

**`DN-013` (MUST):** جدولة إعادة المحاولة بتراجع أسّي (مثلًا: 1د، 5د، 15د، ساعة، 6س، 24س) حتى مهلة قصوى موثَّقة (48–72 ساعة)، ثم `failed` مع إمكانية إعادة المحاولة يدويًا.

## 3. الأمن — منع الاستيلاء على الدومين

**`DN-020` (MUST):** **لا تفعيل بلا تحقق من الملكية.** هذه ليست خطوة تحسينية.

> **لماذا:** بلا تحقق، يمكن لأي شخص ربط `competitor.com` بحسابه. لو وجّه ذلك الدومين يومًا إلينا (أو كان يشير إلينا أصلًا)، يستولي على حركة مروره. وأسوأ: يمكنه استغلال دومين مهجور يشير لنا لبناء صفحة تصيّد تبدو رسمية.

**`DN-021` (MUST):** طرق التحقق المقبولة: سجل `TXT` بقيمة عشوائية فريدة، أو `CNAME` بسجل تحقق مخصص. **الرمز عشوائي بما يكفي وغير قابل للتخمين ومرتبط بموقع واحد فقط.**

**`DN-022` (MUST):** **hostname واحد لا يكون `active` لأكثر من موقع في وقت واحد**، مفروضًا بقيد فريد في قاعدة البيانات (`DM-021`).

**`DN-023` (MUST):** فصل الدومين من موقع ثم ربطه بآخر **يتطلب إعادة تحقق كاملة**.

**`DN-024` (MUST):** كل عمليات الدومين (إضافة، تحقق، تفعيل، فصل، حذف) تُسجَّل في `audit_logs` بالفاعل والوقت.

**`DN-025` (MUST):** ربط الدومين مقيَّد بالـ entitlement ويُفحص server-side (`BE-`).

## 4. التطبيع والتحقق من الصحة

**`DN-030` (MUST):** تطبيع الـ hostname قبل التخزين أو المقارنة:
- تحويل لحروف صغيرة.
- إزالة النقطة الأخيرة (`example.com.` → `example.com`).
- تحويل IDN إلى punycode (`مثال.com` → `xn--mgbh0fb.com`).
- إزالة المسار والمنفذ والبروتوكول لو أُرسلت.

**`DN-031` (MUST):** الـ hostname يُخزَّن **مطبَّعًا دائمًا**. المقارنة تتم على الصيغة المطبَّعة فقط.

> **لماذا:** بلا تطبيع، `Example.COM` و `example.com` و `xn--...` تُعامل كدومينات مختلفة، فيسقط قيد التفرد ويصبح الاستيلاء ممكنًا.

**`DN-032` (MUST):** رفض: عناوين IP، `localhost`، النطاقات الداخلية (`.local`, `.internal`)، الدومينات المحجوزة للمنصة، والدومينات غير صالحة البنية.

**`DN-033` (MUST):** دعم `www` و apex معًا كوحدة واحدة مفهومة: يُربطان معًا مع توجيه موحّد، لا كسجلين منفصلين يربك المستخدم.

## 5. TLS

**`DN-040` (MUST):** الشهادات **آلية بالكامل** عبر Cloudflare for SaaS أو مكافئ. **ممنوع** أي خطوة يدوية لكل عميل.

**`DN-041` (MUST):** التجديد آلي ومراقَب. **تنبيه قبل انتهاء الصلاحية بمدة كافية (≥ 14 يومًا)** لا بعده.

> **لماذا:** شهادة منتهية = متصفح يعرض تحذيرًا مخيفًا لكل زائر. هذا أسوأ من الموقع المعطّل.

**`DN-042` (MUST):** HTTPS إلزامي. HTTP يعيد التوجيه دائمًا (301) إلى HTTPS.

**`DN-043` (MUST):** HSTS مفعّل على الدومينات المؤكدة. **الحذر مع `preload`** لأنه قرار شبه دائم — يحتاج ADR.

**`DN-044` (MUST):** فشل تجهيز الشهادة يبقي الحالة `tls_pending` مع إعادة محاولة خلفية، **ولا** يُظهر الموقع بلا حماية.

## 6. حل الدومين في وقت التشغيل

**`DN-050` (MUST):** الخريطة `hostname → site_id` **مخزَّنة في cache**. هذا أسخن استعلام في المنتج كله.

**`DN-051` (MUST):** عمر الـ cache قصير/متوسط (دقائق)، **مع إبطال فوري صريح** عند: تفعيل، فصل، تغيير slug، تعطيل موقع، أو إيقاف اشتراك.

**`DN-052` (MUST):** hostname غير معروف يرد صفحة خطأ مناسبة **ولا** يخدم موقعًا عشوائيًا ولا يكشف بنية النظام.

**`DN-053` (MUST):** فشل الـ cache (Redis معطل) **لا يُسقط المواقع**: يرجع للقراءة من قاعدة البيانات مع حد للمعدل، ويُطلق تنبيهًا.

**`DN-054` (MUST NOT):** ممنوع الاعتماد على header يتحكم فيه العميل (مثل `X-Forwarded-Host`) لتحديد الموقع، إلا من مصدر موثوق ومُتحقق منه على مستوى البنية التحتية.

> **لماذا:** header قابل للتزوير يعني أن أي شخص يطلب موقع أي عميل بمجرد تغيير رأس الطلب.

## 7. الأنماط الممنوعة

| # | النمط | لماذا هو خطر |
|---|---|---|
| 1 | التفعيل بلا تحقق من الملكية | استيلاء على دومين + تصيّد |
| 2 | استطلاع متزامن للتحقق | مهلة مستنفدة وتجربة سيئة |
| 3 | تخزين hostname بلا تطبيع | كسر التفرد → إمكانية الاستيلاء |
| 4 | نفس الـ hostname نشط لموقعين | توجيه غير محدد |
| 5 | «فشل التحقق» بلا سبب | تذكرة دعم مضمونة |
| 6 | شهادة يدوية لكل عميل | لا يتوسع إطلاقًا |
| 7 | بلا تنبيه قبل انتهاء الشهادة | تحذير أمني لكل زائر |
| 8 | سجل DNS لكل موقع | لا يتوسع + بطء |
| 9 | تخطي الكلمات المحجوزة | تعطيل خدمات المنصة |
| 10 | الثقة في `X-Forwarded-Host` | وصول لأي موقع بتزوير رأس |
| 11 | تغيير slug بلا إعادة توجيه | كسر روابط العميل المنشورة |
| 12 | إعادة محاولة بلا تراجع أسّي | إساءة لمزوّد DNS + حظر |

## 8. الاختبارات المطلوبة

**`DN-060` (MUST):** اختبار التطبيع: `Example.COM.`, `example.com`, ونسخة IDN كلها تُطبَّع لنفس القيمة وتصطدم بقيد التفرد.

**`DN-061` (MUST):** اختبار منع الاستيلاء: مستأجر آخر يحاول إضافة hostname نشط لمستأجر أول → يُرفض.

**`DN-062` (MUST):** اختبار عدم التفعيل بلا تحقق: سجل بحالة `pending_dns` **لا يُخدَم** على الإطلاق.

**`DN-063` (MUST):** اختبار انتقالات الحالة: كل انتقال مسموح يعمل، وكل انتقال غير مسموح يُرفض.

**`DN-064` (MUST):** اختبار الكلمات المحجوزة: كل slug في القائمة يُرفض.

**`DN-065` (MUST):** اختبار الإبطال: فصل دومين → الطلب التالي **لا** يُخدَم من الـ cache.

**`DN-066` (MUST):** اختبار تدهور لطيف: Redis معطل → المواقع تظل تُخدَم من قاعدة البيانات.

## 9. Definition of Done — Domains & SSL

- [ ] الـ hostname مطبَّع قبل التخزين والمقارنة.
- [ ] قيد فريد يمنع hostname نشطًا لموقعين.
- [ ] لا تفعيل بلا تحقق من الملكية.
- [ ] رمز التحقق عشوائي غير قابل للتخمين ومرتبط بموقع واحد.
- [ ] كل الحالات الست مطبَّقة، وكل `failed` تحمل سببًا قابلًا للتصرف.
- [ ] التحقق خلفي بتراجع أسّي ومهلة قصوى.
- [ ] TLS آلي، والتجديد مراقَب بتنبيه مبكر.
- [ ] HTTPS مفروض و HTTP يعيد التوجيه.
- [ ] الخريطة في الـ cache مع إبطال صريح عند كل تغيير.
- [ ] الكلمات المحجوزة مطبَّقة على الـ slugs.
- [ ] تغيير الـ slug يترك إعادة توجيه.
- [ ] لا اعتماد على headers من العميل.
- [ ] تدهور لطيف عند تعطل الـ cache.
- [ ] كل عمليات الدومين في `audit_logs`.
- [ ] تعليمات DNS واضحة وقابلة للنسخ في الواجهة.

---

## 10. ما يحتاج ADR

- تغيير مزوّد TLS/CDN.
- تفعيل HSTS preload.
- السماح بـ nameservers مفوَّضة بالكامل.
- دعم أكثر من دومين نشط لموقع واحد.
- تغيير طريقة التحقق من الملكية.
