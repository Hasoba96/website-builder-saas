# 15 — API Engineering Standards

> **بادئة القواعد:** `API-` · **الحالة:** إلزامي · **المالك:** Backend
> **المرجع الأعلى:** [`../../en/00-PROJECT-RULES.md`](../../en/00-PROJECT-RULES.md) · **نسخة النظام الحاكمة:** [`../../en/systems/15-api-standards.md`](../../en/systems/15-api-standards.md) · هذه ترجمة عربية متزامنة.

---

## 0. الغرض والنطاق

**قاعدة حاكمة:** الـ API **عقد**. ما دخل الاستجابة صار التزامًا على المشروع؛ إزالته أو تغيير معناه يكسر عملاءه. لذلك: **اتساق مبكر أرخص بكثير من إصلاح متأخر.**

**`API-001` (MUST):** REST/JSON في الـ MVP، موثَّق بـ **OpenAPI**. GraphQL ليس ضرورة ويحتاج ADR.

---

## 1. المسارات والإصدارات

**`API-010` (MUST):** كل مسارات Product/Business API تحت `/api/v1/`. مسارا فحص البنية التشغيلية `/health` و`/ready` ليسا Product APIs، وهما مستثنيان صراحة من بادئة إصدار API وفق `IN-004`. لا يضيف هذا الاستثناء أي endpoint آخر.

**`API-011` (MUST):** مسارات Product/Business API بصيغة `kebab-case` و**الجمع**، والهرمية تعكس الملكية. يحتفظ مسارا الفحص التشغيلي باسميهما المحددين وفق `API-010` و`IN-004`:

```
GET    /api/v1/websites
POST   /api/v1/websites
GET    /api/v1/websites/{websiteId}
PATCH  /api/v1/websites/{websiteId}
GET    /api/v1/websites/{websiteId}/pages
POST   /api/v1/websites/{websiteId}/publish
GET    /api/v1/websites/{websiteId}/leads
```

**`API-012` (MUST NOT):** ممنوع الأفعال في المسار إلا للعمليات التي ليست CRUD حقيقيًا (`/publish`, `/rollback`, `/verify`). `POST /api/v1/getWebsites` خطأ.

**`API-013` (MUST):** حقول JSON `camelCase` دائمًا — في الطلب والاستجابة.

**`API-014` (MUST):** التغيير الكاسر يتطلب إصدارًا جديدًا. الكاسر يشمل: حذف حقل، تغيير نوعه، تغيير معناه، جعل اختياري إلزاميًا، تضييق قيم مقبولة.

**`API-015` (MUST):** إضافة حقل اختياري **ليست كاسرة**. العملاء يجب أن يتجاهلوا الحقول غير المعروفة.

## 2. الاستجابات

**`API-020` (MUST):** شكل موحّد للنجاح:

```json
{ "data": { ... } }
{ "data": [ ... ], "pagination": { "nextCursor": "...", "hasMore": true } }
```

**`API-021` (MUST):** شكل موحّد للخطأ — **بلا استثناء**:

```json
{
  "error": {
    "code": "DOMAIN_NOT_VERIFIED",
    "message": "Domain verification is still pending",
    "details": { "hostname": "example.com", "status": "pending_dns" },
    "requestId": "req_01J..."
  }
}
```

**`API-022` (MUST):** `code` **ثابت وقابل للقراءة آليًا** بـ `SCREAMING_SNAKE_CASE`. العميل يتفرع على `code`، لا على نص `message`.

> **لماذا:** نص الرسالة يتغير مع الترجمة والتحسين. الكود عقد ثابت.

**`API-023` (MUST):** `requestId` في **كل** استجابة (نجاح وفشل) وفي رأس الاستجابة أيضًا.

> **لماذا:** العميل يبلّغ عن مشكلة برقم واحد، ونجد كل سياقها في السجلات فورًا — بدل البحث بالوقت التقريبي.

**`API-024` (MUST NOT):** **ممنوع** تسريب رسائل الاستثناءات الداخلية أو الـ stack traces أو تفاصيل قاعدة البيانات (`CORE-062`).

**`API-025` (MUST):** الاستجابة تُبنى من **DTO صريح**، لا من صف قاعدة البيانات (`CORE-033`).

---

## 3. رموز الحالة

**`API-030` (MUST):** الاستخدام الدقيق:

| الرمز | متى |
|---|---|
| `200` | نجاح مع محتوى |
| `201` | إنشاء مورد (مع `Location`) |
| `202` | عملية غير متزامنة قُبلت (نشر، توليد AI) |
| `204` | نجاح بلا محتوى |
| `400` | طلب مشوَّه بنيويًا |
| `401` | غير مصادق أو جلسة منتهية |
| `403` | مصادق لكن ممنوع (دور أو حد خطة) |
| `404` | غير موجود **أو** لا ينتمي للمستأجر (`MT-014`) |
| `409` | تعارض نسخ أو حالة (`VE-022`) |
| `422` | صحيح بنيويًا لكن فشل التحقق الدلالي |
| `429` | تجاوز الحد (مع `Retry-After`) |
| `500` | خطأ داخلي غير متوقع |
| `503` | الخدمة غير متاحة مؤقتًا (قاطع دائرة مفتوح) |

**`API-031` (MUST):** التمييز بين `400` (JSON مشوَّه، نوع خاطئ) و `422` (بنية صحيحة، قيمة غير مقبولة) **ثابت في المشروع كله**.

**`API-032` (MUST):** `429` يحمل `Retry-After` دائمًا.

**`API-033` (MUST NOT):** ممنوع `200` مع خطأ في الجسم. رمز الحالة جزء من العقد.

---

## 4. التحقق من المدخلات

**`API-034` (MUST):** كل مدخل يُتحقق منه بـ schema من `packages/schemas` (`CORE-022`). **لا ثقة بأي حمولة من العميل** (`CORE-005`).

**`API-035` (MUST):** الـ schemas `.strict()` — الحقول غير المعروفة تُرفض (`CE-012`).

**`API-036` (MUST):** أخطاء التحقق تُرجع **كل** المشاكل دفعة واحدة، لا واحدة في كل مرة:

```json
{
  "error": {
    "code": "VALIDATION_FAILED",
    "details": {
      "fields": [
        { "path": "title",       "code": "TOO_LONG",  "max": 120 },
        { "path": "cta.href",    "code": "INVALID_PROTOCOL" }
      ]
    },
    "requestId": "req_01J..."
  }
}
```

> **لماذا:** إرجاع خطأ واحد في كل مرة يجبر المستخدم على دورات إصلاح متكررة مُحبِطة.

**`API-037` (MUST):** حدود صارمة: حجم الطلب · عمق الـ JSON · عدد عناصر المصفوفات · طول كل نص (`SE-053`).

---

## 5. الترقيم والقوائم

**`API-040` (MUST):** الترقيم **cursor-based** للقوائم الكبيرة، لا `OFFSET`.

> **لماذا:** `OFFSET` يبطؤ خطيًا مع العمق، وينتج نتائج مكررة أو مفقودة عند تغيّر البيانات أثناء التصفح.

**`API-041` (MUST):** حد أقصى مفروض في الخادم مهما طلب العميل (مثلًا `limit ≤ 100`).

**`API-042` (MUST):** الـ cursor **معتم (opaque)** للعميل. ممنوع أن يبني العميل cursor بنفسه أو يعتمد على بنيته.

**`API-043` (MUST):** ترتيب ثابت ومحدَّد لكل قائمة، وإلا كان الترقيم غير حتمي.

**`API-044` (MUST):** الفلاتر والفرز من **قائمة بيضاء** لأسماء الحقول. ممنوع تمرير مدخل العميل مباشرةً إلى `ORDER BY`.

---

## 6. الـ Idempotency

**`API-050` (MUST):** رأس `Idempotency-Key` مدعوم في: النشر · إنشاء الاشتراك · أي عملية دفع · أي عملية إنشاء يكلّف تكرارها.

**`API-051` (MUST):** نفس المفتاح بنفس الحمولة خلال النافذة المحددة → **نفس الاستجابة**، بلا تنفيذ ثانٍ.

**`API-052` (MUST):** نفس المفتاح بحمولة **مختلفة** → `409` صريح. هذا خطأ في العميل ويجب أن يُكشف لا أن يُبتلع.

**`API-053` (MUST):** نافذة الاحتفاظ بالمفاتيح موثَّقة (24 ساعة مثلًا).

---

## 7. الأمن على مستوى الـ API

**`API-060` (MUST):** كل endpoint غير عام خلف حارس مصادقة وتفويض (`AU-031`)، والافتراضي **المنع** (`AU-033`).

**`API-061` (MUST):** rate limiting على كل المسارات، خصوصًا العامة (`SE-050`).

**`API-062` (MUST):** CORS مضبوط بقائمة أصول محددة. **ممنوع `*` مع credentials**.

**`API-063` (MUST):** كل استجابة تُراجَع لعدم تسريب حقول داخلية (`MT-026`).

**`API-064` (MUST):** العمليات الحساسة تُسجَّل في `audit_logs` (`SE-070`).

---

## 8. التوثيق

**`API-070` (MUST):** OpenAPI **مولَّد من الـ schemas** لا مكتوب يدويًا — وإلا انحرف عن الواقع خلال أسابيع.

**`API-071` (MUST):** كل endpoint موثَّق بـ: الغرض · المصادقة المطلوبة · الدور المطلوب · الحدود · أكواد الأخطاء الممكنة · مثال.

**`API-072` (MUST):** تحديث التوثيق جزء من `Definition of Done`، لا مهمة لاحقة.

## 9. الأنماط الممنوعة

| # | النمط | لماذا هو خطر |
|---|---|---|
| 1 | أشكال أخطاء مختلفة بين endpoints | العميل يكتب معالجة خاصة لكل واحد |
| 2 | `200` مع خطأ في الجسم | يخالف العقد ويربك كل عميل |
| 3 | تسريب stack trace | استطلاع مجاني للمهاجم |
| 4 | صف قاعدة بيانات كاستجابة | تسريب حقول داخلية مستقبلية |
| 5 | `OFFSET` للقوائم الكبيرة | بطء + نتائج مكررة أو مفقودة |
| 6 | قائمة بلا حد أقصى | استجابة ضخمة تُسقط الخدمة |
| 7 | فرز بمدخل العميل مباشرةً | حقن SQL أو تسريب بنية |
| 8 | تفرّع العميل على نص الرسالة | يكسر عند أي تحسين للنص |
| 9 | بلا `requestId` | تشخيص شبه مستحيل |
| 10 | خطأ تحقق واحد في كل مرة | تجربة محبطة |
| 11 | `CORS: *` مع credentials | سرقة بيانات عبر الأصول |
| 12 | حقول `snake_case` في JSON | تعارض مع معايير المشروع |
| 13 | تغيير كاسر بلا إصدار | كسر صامت لكل العملاء |
| 14 | نفس idempotency key بحمولة مختلفة يُبتلع | خطأ عميل يتحول لبيانات فاسدة |

## 10. الاختبارات المطلوبة

**`API-080` (MUST):** اختبار عقد لكل endpoint: شكل النجاح وشكل الخطأ يطابقان المعيار.

**`API-081` (MUST):** اختبار رموز الحالة: كل حالة خطأ ترجع الرمز الصحيح (خصوصًا `403` مقابل `404`).

**`API-082` (MUST):** اختبار التحقق: حقول زائدة مرفوضة، وكل الأخطاء ترجع دفعة واحدة.

**`API-083` (MUST):** اختبار الترقيم: الحد الأقصى مفروض، والـ cursor يعمل، ولا تكرار ولا فقد.

**`API-084` (MUST):** اختبار idempotency: تكرار بنفس المفتاح → نفس النتيجة؛ بحمولة مختلفة → `409`.

**`API-085` (MUST):** اختبار عدم التسريب: لا حقول داخلية ولا stack traces في أي استجابة.

**`API-086` (MUST):** اختبار `requestId`: موجود في كل استجابة وفي الرأس.

## 11. Definition of Done — API

- [ ] مسار Product/Business API تحت `/api/v1/`، `kebab-case`، جمع، هرمي؛ مسارا الفحص التشغيلي هما `/health` و`/ready` بالضبط (`IN-004`).
- [ ] حقول JSON `camelCase`.
- [ ] شكل النجاح والخطأ يطابق المعيار.
- [ ] `code` ثابت، و`requestId` في كل استجابة وفي الرأس.
- [ ] رمز الحالة صحيح حسب الجدول.
- [ ] التحقق بـ schema مشترك `.strict()`، وكل الأخطاء دفعة واحدة.
- [ ] حدود الحجم والعمق مطبَّقة.
- [ ] الترقيم cursor-based بحد أقصى مفروض.
- [ ] الفلاتر والفرز من قائمة بيضاء.
- [ ] `Idempotency-Key` مدعوم حيث يلزم ومختبَر.
- [ ] الحارس مطبَّق، والافتراضي المنع.
- [ ] Rate limit مهيّأ.
- [ ] CORS محدد بأصول معروفة.
- [ ] الاستجابة من DTO صريح بلا تسريب.
- [ ] OpenAPI مولَّد ومحدَّث.
- [ ] العمليات الحساسة في `audit_logs`.

---

## 12. ما يحتاج ADR

- إضافة GraphQL أو gRPC.
- إصدار `v2` من الـ API.
- فتح API عام للعملاء أو لمطورين خارجيين.
- تغيير شكل الخطأ الموحّد.
- تغيير استراتيجية الترقيم.
