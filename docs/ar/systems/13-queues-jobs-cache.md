# 13 — Cache, Queues & Background Jobs

> **بادئة القواعد:** `QJ-` · **الحالة:** إلزامي · **المالك:** Backend
> **المرجع الأعلى:** [`../../en/00-PROJECT-RULES.md`](../../en/00-PROJECT-RULES.md) · **نسخة النظام الحاكمة:** [`../../en/systems/13-queues-jobs-cache.md`](../../en/systems/13-queues-jobs-cache.md) · هذه ترجمة عربية متزامنة.
> **يحقق المبدأ:** `CORE-015` (Async for slow work)

---

## 0. القاعدة الحاكمة

> ### `QJ-001` (MUST NOT)
> **Redis ليس مصدر حقيقة.** أي بيانات لا يمكن إعادة بنائها من PostgreSQL **ممنوع** أن تعيش في Redis وحده.
> افترض دائمًا أن Redis قد يُمسح بالكامل في أي لحظة. لو كان ذلك يعني فقد بيانات عميل — فالتصميم خاطئ.

---

## 1. استخدامات Redis

**`QJ-010` (MUST):** الاستخدامات المسموحة حصريًا:

| الاستخدام | ملاحظة |
|---|---|
| خريطة `domain → site_id` | أسخن قراءة في المنتج |
| Cache تهيئة الموقع الساخنة | مشتقة من الـ DB |
| Rate limiting | فقدها يعني فتح مؤقت للحدود، لا فقد بيانات |
| الجلسات (لو اختيرت) | فقدها يعني تسجيل خروج، لا فقد بيانات |
| طوابير BullMQ | الوظائف الحرجة لها سجل في الـ DB |
| أقفال قصيرة العمر ومساعدات idempotency | — |

**`QJ-011` (MUST):** لكل مفتاح Redis/cache يملكه التطبيق **TTL صريح**. مفاتيح BullMQ الداخلية تتبع lifecycle المكتبة بدلًا من ذلك: تُضبط حدود الاحتفاظ بالوظائف والموارد؛ يُمنع فرض TTL يدوي أو تعديل المفاتيح الداخلية يدويًا. الاحتفاظ لا يعني أن كل مفتاح داخلي ينتهي بـTTL.

**`QJ-012` (MUST):** تحمل مفاتيح Redis/cache التي يملكها التطبيق scope صريحًا للمستأجر/الموقع عند تخزين بياناته (`MT-042`)، أو ملكية تطبيق صريحة للبيانات غير المرتبطة بمستأجر. تستخدم مفاتيح BullMQ الداخلية namespace للبيئة/الطابور عبر prefix المدعوم من BullMQ، وليس tenant prefix حرفيًا مفروضًا أو `ioredis.keyPrefix` غير المتوافق. لا يعوّض namespace التحقق من ملكية المستأجر في payloads/workers للوظائف الحقيقية (`QJ-033`).

تحتاج اتصالات BullMQ سياسة صريحة لفشل producer وإعادة اتصال worker، وإغلاقًا منظمًا، وحدًا كليًا لسلوك الانقطاع/التعافي. يُمنع infinite producer retries و`FLUSHALL`. يبقى Redis غير مصدر حقيقة (`QJ-001`)؛ لا تعيش حالة أعمال حرجة في BullMQ وحده (`QJ-045`). لا توجد Product Jobs في Stage 00؛ يُسمح باختبار technical queue lifecycle داخل بيئة الاختبار عند الحاجة لإثبات Foundation، دون بيانات Tenant/Domain مصطنعة.

**`QJ-013` (MUST):** تعطل Redis **لا يُسقط المنتج**: القراءات ترجع لقاعدة البيانات مع حد للمعدل، والكتابات الحرجة تستمر، ويُطلق تنبيه (`DN-053`).

## 2. الطوابير

**`QJ-020` (MUST):** الطوابير المعرَّفة:

| الطابور | الوظائف | الأولوية |
|---|---|---|
| `ai` | توليد blueprint ومحتوى وصور | عالية (ينتظرها المستخدم) |
| `media` | تحسين، نسخ متعددة، تنظيف | متوسطة |
| `domains` | تحقق، مزامنة حالة TLS | عالية |
| `publish` | بناء اللقطة والنشر | **حرجة** |
| `notifications` | بريد، webhooks، رسائل | عالية |
| `analytics` | تجميع، تلخيصات | منخفضة |
| `maintenance` | تنظيف، احتفاظ، أصول يتيمة | منخفضة |

**`QJ-021` (MUST):** فصل الطوابير **إلزامي**. ممنوع طابور واحد لكل شيء.

> **لماذا:** تراكم آلاف وظائف الـ analytics يجب ألا يؤخر نشر موقع عميل ينتظره الآن. الفصل يحمي المسارات الحرجة من الحمل المنخفض الأولوية.

**`QJ-022` (MUST):** لكل طابور **عدد workers محدود ومضبوط**، بحيث لا يستطيع طابور واحد استهلاك كل موارد قاعدة البيانات أو الذاكرة.

**`QJ-023` (MUST):** الطوابير ذات الأولوية المنخفضة تُخنق (throttle) تلقائيًا عند ارتفاع الحمل على الأنظمة المشتركة.

## 3. تصميم الوظائف

**`QJ-030` (MUST):** كل وظيفة **idempotent** أو تحمل **idempotency key**.

> **لماذا:** إعادة التنفيذ ليست استثناءً — هي السلوك الطبيعي. الـ worker قد يموت بعد إتمام العمل وقبل تسجيل النجاح، فتُعاد الوظيفة. بلا idempotency: بريد مكرر، فوترة مزدوجة، نسخة نشر مكررة.

**`QJ-031` (MUST):** الحمولة **صغيرة ومرجعية**: معرّفات لا بيانات كاملة.

```ts
// ✅ صحيح
{ jobId, organizationId, websiteId, assetId, requestedBy }

// ❌ خطأ: حمولة ضخمة، وبيانات قديمة وقت التنفيذ، ومحتوى حساس في Redis
{ asset: { ...fullBinaryMetadata }, site: { ...entireSnapshot } }
```

**`QJ-032` (MUST):** الـ worker **يقرأ الحالة الحالية** من قاعدة البيانات عند التنفيذ، ولا يثق بما في الحمولة كحقيقة راهنة.

**`QJ-033` (MUST):** الحمولة تحمل scope المستأجر، والـ worker **يعيد التحقق من الملكية والصلاحية** (`MT-044`).

**`QJ-034` (MUST):** كل وظيفة لها **مهلة تنفيذ قصوى صريحة**، وتُنهى عند تجاوزها.

**`QJ-035` (MUST NOT):** ممنوع أن تطلق وظيفة عددًا غير محدود من الوظائف الفرعية. التوسع (fan-out) محدود ومقاس.

**`QJ-036` (MUST):** الوظيفة الطويلة تُقسَّم إلى **دفعات قابلة للاستئناف**، لا تُنفَّذ ككتلة واحدة قد تفشل في نهايتها.

## 4. الفشل وإعادة المحاولة

**`QJ-040` (MUST):** إعادة المحاولة بـ **تراجع أسّي (exponential backoff)** مع تشويش عشوائي (jitter) وحد أقصى للمحاولات.

> **لماذا التشويش:** بدونه، كل الوظائف الفاشلة في نفس اللحظة تعيد المحاولة في نفس اللحظة — فتضرب الخدمة المتعافية دفعة واحدة وتسقطها ثانية (thundering herd).

**`QJ-041` (MUST):** التمييز بين نوعي الفشل:

| النوع | مثال | السلوك |
|---|---|---|
| **عابر (transient)** | مهلة شبكة، `503`، rate limit | إعادة محاولة |
| **دائم (permanent)** | بيانات غير صالحة، مورد محذوف، صلاحية مرفوضة | **بلا إعادة محاولة** → فشل فوري |

> **لماذا:** إعادة محاولة خطأ دائم 10 مرات تهدر الموارد وتؤخر اكتشاف المشكلة الحقيقية.

**`QJ-042` (MUST):** الفشل النهائي يذهب إلى **طابور الرسائل الميتة (DLQ)** مع سياقه الكامل.

**`QJ-043` (MUST):** الـ DLQ **مراقَب** ويطلق تنبيهًا. طابور ميت لا ينظر إليه أحد = أعطال صامتة تتراكم.

**`QJ-044` (MUST):** إعادة تشغيل وظيفة من الـ DLQ ممكنة بعد إصلاح السبب.

**`QJ-045` (MUST):** الوظائف الحرجة (النشر، الفوترة، الإشعارات) لها **سجل حالة في قاعدة البيانات** لا في Redis وحده.

> **لماذا:** لو مُسح Redis، يجب أن نعرف أي عمليات نشر كانت جارية وما مصيرها. بلا سجل دائم، تختفي بلا أثر.

## 5. الـ Cache

**`QJ-050` (MUST):** بنية المفتاح الموحّدة (`CORE-6.4`):

```
<scope>:<entity>:<id>[:<qualifier>]

site:config:site_01J:v42
domain:map:example.com
org:usage:org_01J:storage
ratelimit:form:site_01J:1.2.3.4
```

**`QJ-051` (MUST):** الإبطال **صريح ومستهدف** عند تغيّر المصدر. الاعتماد على انتهاء TTL وحده يعني أن المستخدم يرى بياناته القديمة بعد التعديل.

**`QJ-052` (MUST NOT):** ممنوع الإبطال الشامل (`FLUSHALL` أو مسح بنمط واسع) في الإنتاج.

**`QJ-053` (MUST):** حماية من **انهيار الـ cache (stampede)**: عند انتهاء مفتاح ساخن، طلب واحد فقط يعيد بناءه والباقي ينتظر أو يستخدم القيمة القديمة قليلًا.

> **لماذا:** بلا حماية، انتهاء مفتاح دومين شائع يعني آلاف الطلبات المتزامنة تضرب قاعدة البيانات في نفس الجزء من الثانية.

**`QJ-054` (MUST NOT):** ممنوع تخزين بيانات لوحة تحكم حساسة بمفتاح قد يُشارك بين مستأجرين (`MT-043`).

**`QJ-055` (MUST):** فشل قراءة الـ cache يُعامل كـ **miss**، لا كخطأ يوقف الطلب.

---

## 6. الأقفال والتزامن

**`QJ-060` (MUST):** الأقفال الموزعة **قصيرة العمر** وبـ TTL إلزامي. قفل بلا انتهاء = مورد معطَّل للأبد عند موت الـ worker.

**`QJ-061` (MUST):** حامل القفل هو وحده من يحرره (رمز ملكية)، لا أي عملية أخرى.

**`QJ-062` (MUST):** الوظائف الدورية المجدولة محمية من **التشغيل المتزامن** (قفل أو آلية تجاهل التداخل).

> **لماذا:** وظيفة تجميع تعمل مرتين في نفس اللحظة قد تضاعف الأرقام أو تتصارع على نفس الصفوف.

**`QJ-063` (MUST):** ممنوع الاعتماد على القفل كبديل عن التصميم الـ idempotent. القفل يقلل التصادم؛ الـ idempotency هي الضمان الحقيقي.

## 7. الأنماط الممنوعة

| # | النمط | لماذا هو خطر |
|---|---|---|
| 1 | Redis كمصدر حقيقة | فقد بيانات عند أول مسح |
| 2 | مفتاح يملكه التطبيق بلا TTL | تسرب ذاكرة حتى الامتلاء |
| 3 | طابور واحد لكل شيء | التجميع يؤخر نشر العميل |
| 4 | وظيفة غير idempotent | بريد مكرر / فوترة مزدوجة |
| 5 | حمولة ضخمة | بيانات قديمة + ضغط على Redis |
| 6 | الثقة في الحمولة كحقيقة راهنة | العمل على حالة تغيّرت |
| 7 | إعادة محاولة بلا تراجع أسّي | إسقاط الخدمة المتعافية |
| 8 | إعادة محاولة بلا jitter | thundering herd |
| 9 | إعادة محاولة خطأ دائم | هدر موارد وتأخير الاكتشاف |
| 10 | DLQ بلا مراقبة | أعطال صامتة تتراكم |
| 11 | حالة النشر في Redis فقط | ضياع أثر العمليات عند المسح |
| 12 | `FLUSHALL` في الإنتاج | انهيار أداء كامل |
| 13 | بلا حماية من stampede | قاعدة البيانات تُضرب دفعة واحدة |
| 14 | قفل بلا TTL | مورد معطَّل للأبد |
| 15 | fan-out غير محدود | انفجار الطابور |

## 8. المراقبة المطلوبة

**`QJ-070` (MUST):** مقاييس إلزامية لكل طابور: عمق الطابور · معدل المعالجة · زمن الانتظار · زمن التنفيذ · معدل الفشل · عمق الـ DLQ.

**`QJ-071` (MUST):** تنبيهات على: عمق طابور يتجاوز عتبة · وظيفة عالقة أطول من مهلتها · أي عنصر في DLQ حرج · معدل فشل يتجاوز العتبة.

**`QJ-072` (MUST):** كل تنفيذ وظيفة يُسجَّل بـ `jobId` و `requestId` و scope المستأجر (`MT-046`).

## 9. الاختبارات المطلوبة

**`QJ-080` (MUST):** اختبار idempotency لكل وظيفة: التنفيذ مرتين ينتج أثرًا واحدًا.

**`QJ-081` (MUST):** اختبار تغيّر الحالة: حذف المورد بعد الجدولة وقبل التنفيذ → الوظيفة تفشل بلطف ولا تنهار.

**`QJ-082` (MUST):** اختبار تصنيف الفشل: خطأ دائم لا يُعاد، وخطأ عابر يُعاد ضمن الحد.

**`QJ-083` (MUST):** اختبار الـ DLQ: تجاوز حد المحاولات → الوظيفة في الـ DLQ بسياقها.

**`QJ-084` (MUST):** اختبار الإبطال: تعديل المصدر → القراءة التالية **لا** تأتي من الـ cache القديم.

**`QJ-085` (MUST):** اختبار تعطل Redis: الخدمات الحرجة تظل تعمل.

**`QJ-086` (MUST):** اختبار العزل: وظيفة مستأجر لا تصل لبيانات مستأجر آخر (`MT-061`).

## 10. Definition of Done — Queues & Cache

- [ ] لا بيانات غير قابلة لإعادة البناء في Redis وحده.
- [ ] مفاتيح التطبيق لها TTL وscope ملكية؛ مفاتيح BullMQ الداخلية تستخدم namespaces مدعومة وlifecycle retention وحدود موارد (`QJ-011`, `QJ-012`).
- [ ] الوظيفة على الطابور الصحيح حسب الأولوية.
- [ ] الوظيفة idempotent أو تحمل idempotency key.
- [ ] الحمولة مرجعية صغيرة، والـ worker يقرأ الحالة الحالية.
- [ ] الـ worker يعيد التحقق من الملكية والصلاحية.
- [ ] مهلة تنفيذ قصوى صريحة.
- [ ] تراجع أسّي + jitter + حد أقصى للمحاولات.
- [ ] التمييز بين الفشل العابر والدائم.
- [ ] DLQ مهيَّأ ومراقَب بتنبيه.
- [ ] الوظائف الحرجة لها سجل حالة في قاعدة البيانات.
- [ ] الإبطال صريح ومستهدف، بلا مسح شامل.
- [ ] حماية من stampede للمفاتيح الساخنة.
- [ ] الأقفال بـ TTL ورمز ملكية.
- [ ] fan-out محدود.
- [ ] المقاييس والتنبيهات مهيَّأة.

## 11. ما يحتاج ADR

- تغيير نظام الطوابير (BullMQ → غيره).
- إضافة وسيط رسائل ثانٍ (Kafka وغيره).
- Redis كمصدر حقيقة لأي بيانات.
- تغيير استراتيجية الـ cache جوهريًا.
- تشغيل workers في خدمة منفصلة تمامًا.
