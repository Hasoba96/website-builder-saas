## 0. الغرض والنطاق

هذا النظام يحدد **ما يراه العالم**. أي خطأ هنا يظهر مباشرةً لزوار مواقع عملائنا — لا في لوحة تحكم داخلية.

**قاعدة حاكمة:** الـ draft والـ published **عالمان منفصلان تمامًا**. المحرّر يكتب في الأول؛ الزوار يقرأون من الثاني؛ ولا جسر بينهما إلا عملية Publish الصريحة.

---

## 1. نموذج النسخ (Revisions)

```
Editor ──► Draft Revision ──[Publish]──► Immutable Published Revision ──► Renderer ──► الزائر
            (متغيّرة)                      (لا تتغير أبدًا)
```

**`RP-001` (MUST):** لكل موقع **نسخة draft واحدة** قابلة للتعديل، و**سلسلة نسخ منشورة غير قابلة للتعديل**.

**`RP-002` (MUST NOT):** **النسخة المنشورة لا تُعدَّل أبدًا بعد إنشائها.** أي تغيير يُنتج نسخة جديدة برقم إصدار أعلى.

> **لماذا:** لو كانت النسخة المنشورة قابلة للتعديل، لظهرت تعديلات نصف مكتملة للزوار أثناء التحرير — وهذا يعني أن عميلًا قد يعرض موقعه على عميله وهو مكسور.

**`RP-003` (MUST):** `websites.published_revision_id` يشير للنسخة الحية حاليًا. **تبديل هذا المؤشر هو عملية النشر الذرّية.**

**`RP-004` (MUST):** رقم الإصدار (`version`) عدد صحيح تصاعدي لكل موقع، ولا يُعاد استخدامه.

**`RP-005` (MUST):** النسخة المنشورة **لقطة مكتفية بذاتها (self-contained)**: تحتوي كل الصفحات والأقسام والـ theme ومراجع الأصول اللازمة للرندر بلا الرجوع للـ draft.

> **لماذا:** الاعتماد على قراءة جداول حية يعني أن تعديلًا في الـ draft قد يسرّب نفسه للموقع المنشور — وأن عرض موقع منشور يتطلب عشرات الاستعلامات.

**`RP-006` (MUST):** اللقطة تحتوي `schemaVersion` لكل section، ليعرف الـ renderer كيف يعرضها حتى بعد تطور الـ schemas (`CE-023`).

## 2. عملية النشر

```
POST /api/v1/websites/{websiteId}/publish
Idempotency-Key: 01J...
{ "expectedDraftVersion": 42 }

202 Accepted
{ "jobId": "job_...", "status": "queued" }
```

**`RP-010` (MUST):** النشر **عملية غير متزامنة** ترد `202` فورًا. الواجهة تتابع الحالة.

**`RP-011` (MUST):** النشر يقبل `expectedDraftVersion`. لو اختلفت النسخة → `409` (شخص آخر عدّل أثناء ذلك).

**`RP-012` (MUST):** النشر **idempotent** عبر `Idempotency-Key`. تكرار نفس الطلب لا يُنتج نسختين. راجع [`15-api-standards.md`](15-api-standards.md).

**`RP-013` (MUST):** خطوات النشر بهذا الترتيب بالضبط:

```
1. تحقق من الصلاحية والـ entitlement
2. تحقق من صحة الـ draft كاملًا (كل section ضد schema)
3. تحقق من قواعد النشر (صفحة رئيسية موجودة، slugs صالحة، لا مراجع أصول مكسورة)
4. ابنِ اللقطة (snapshot)
5. احفظ النسخة الجديدة بحالة "building"
6. علّمها "published" وبدّل مؤشر published_revision_id  ← ذرّية
7. أبطل مفاتيح الـ cache للموقع المتأثر فقط
8. أطلق حدث WebsitePublished
9. سجّل في audit_logs
```

**`RP-014` (MUST):** **لو فشلت أي خطوة قبل 6، لا تُستبدل النسخة الحية إطلاقًا.** الموقع الحالي يظل يعمل كما هو.

**`RP-015` (MUST):** فشل النشر يعطي المستخدم **سببًا مفهومًا وقابلًا للتصرف** («الصفحة الرئيسية تحتوي قسمًا ببيانات ناقصة: العنوان مطلوب»)، لا «حدث خطأ».

**`RP-016` (MUST):** التحقق يتم على **الـ draft كاملًا** قبل النشر، لا على ما تغيّر فقط. نسخة منشورة نصف صالحة غير مقبولة.

## 3. الرجوع (Rollback)

**`RP-020` (MUST):** الرجوع = **إعادة تفعيل نسخة منشورة سابقة** بتبديل المؤشر. ليس تعديلًا ولا حذفًا.

**`RP-021` (MUST):** الرجوع **فوري** ولا يتطلب إعادة بناء. هذا هو مبرر وجود اللقطات أصلًا.

**`RP-022` (MUST):** يُحتفظ بآخر **N نسخة منشورة** (N ≥ 10 في الـ MVP) قبل التنظيف. راجع [`21-backup-dr-retention.md`](21-backup-dr-retention.md).

**`RP-023` (MUST):** الرجوع **لا يعدّل الـ draft**. المستخدم قد يرجع للنسخة الحية القديمة ويظل يعمل على تعديلاته.

**`RP-024` (MUST):** كل عملية رجوع تُسجَّل في `audit_logs` بالفاعل والنسختين.

## 4. مسؤوليات الـ Renderer

**`RP-030` (MUST):** الـ renderer يقرأ **النسخة المنشورة فقط** (`MT-051`). لا يوجد مسار — ولا معامل، ولا header، ولا cookie — يجعله يعرض draft على نطاق عام.

**`RP-031` (MUST):** معاينة الـ draft (لو وُجدت) تكون على **مسار مصادَق عليه منفصل تمامًا**، مع `X-Robots-Tag: noindex` و `Cache-Control: no-store`.

**`RP-032` (MUST):** الـ renderer يحل `hostname → site_id` من جدول الدومينات المعتمد، ثم يقرأ اللقطة. راجع [`07-domains-ssl.md`](07-domains-ssl.md).

**`RP-033` (MUST):** الـ renderer يختار المكوّن من السجل بناءً على `type` + `variant` + `schemaVersion` (`CE-050`).

**`RP-034` (MUST):** `type`/`variant` غير معروف **يُتخطى بصمت** مع تسجيل تحذير — ولا يُسقط الصفحة (`CE-052`).

**`RP-035` (MUST NOT):** **ممنوع** أن يكشف الـ HTML المنشور: معرّفات داخلية، `organization_id`، `revisionId` بصيغة قابلة للتخمين، بريد المالك، حالة الاشتراك، أو أي بيانات إدارية (`MT-052`).

**`RP-036` (MUST):** الـ renderer **لا يقرأ سياق مستخدم ولا جلسة**. الزائر مجهول دائمًا.

## 5. SEO والبيانات الوصفية

**`RP-040` (MUST):** كل صفحة منشورة تُنتج: `<title>` فريد، `meta description`، `canonical`، Open Graph، `lang` و `dir` صحيحين.

**`RP-041` (MUST):** `sitemap.xml` و `robots.txt` مولَّدان تلقائيًا لكل موقع منشور ويعكسان الصفحات الفعلية.

**`RP-042` (MUST):** الصفحات غير المنشورة والمخفية **لا تظهر** في `sitemap.xml`.

**`RP-043` (MUST):** الموقع على **subdomain المنصة** ونسخته على **الدومين المخصص** لا يتنافسان في محركات البحث: بعد تفعيل الدومين المخصص، إما إعادة توجيه دائمة من الـ subdomain، أو `canonical` يشير للدومين المخصص. القرار موحّد وموثَّق.

**`RP-044` (MUST):** `hreflang` يُطبَّق عند وجود أكثر من لغة لنفس المحتوى. راجع [`23-i18n-rtl.md`](23-i18n-rtl.md).

**`RP-045` (MUST):** الموقع غير المنشور أو المعطَّل يرد `404` أو صفحة حالة مناسبة **مع** `noindex`. **ممنوع** أن يُفهرس محرك بحث موقعًا معطلًا.

## 6. الأداء واستراتيجية العرض

**`RP-050` (MUST):** الطلب العام المعتاد يُخدَم من **CDN/Edge** أو من الـ renderer بـ **قراءة واحدة للقطة** — لا سلسلة استعلامات لكل section (`CORE-014`).

**`RP-051` (MUST):** مفتاح الـ cache للصفحة المنشورة: `hostname + path + publishedRevisionId`.

> **لماذا `publishedRevisionId` في المفتاح:** الإبطال يصبح تلقائيًا. النسخة الجديدة = مفتاح جديد = لا حاجة لمسح دقيق ولا خطر لعرض محتوى قديم.

**`RP-052` (MUST):** عند النشر، الإبطال يشمل **الموقع المتأثر فقط**. ممنوع مسح شامل للـ cache.

**`RP-053` (MUST NOT):** ممنوع N+1 في مسار الرندر (`CORE-066`).

**`RP-054` (MUST):** استراتيجية العرض (SSR / ISR / edge / static) **قرار قابل للقياس والتغيير**، لا عقيدة. المعايير: عدد المواقع، معدل التغيير، تكلفة الإبطال، والحاجة لكتل ديناميكية. تغييرها يحتاج ADR.

**`RP-055` (MUST):** لا يُبنى ملف HTML ثابت منفصل لكل موقع في الـ MVP. هذا لا يتناسب مع مئات الآلاف من المواقع.

**`RP-056` (MUST):** الأصول (صور، خطوط، CSS) تُخدم بروابط **immutable** مع content hash وعمر cache طويل.

## 7. الأنماط الممنوعة

| # | النمط | لماذا هو خطر |
|---|---|---|
| 1 | الـ renderer يقرأ الـ draft | تعديلات نصف مكتملة تظهر للزوار |
| 2 | تعديل نسخة منشورة في مكانها | فقد القدرة على الرجوع + ظهور تغييرات جزئية |
| 3 | النشر يستبدل الحي قبل التحقق | فشل في المنتصف = موقع مكسور |
| 4 | نشر متزامن داخل الطلب | مهلة مستنفدة على المواقع الكبيرة |
| 5 | اللقطة تشير لجداول حية | تسرب draft + استعلامات كثيرة |
| 6 | مفتاح cache بلا `revisionId` | محتوى قديم بعد النشر |
| 7 | مسح شامل للـ cache عند كل نشر | انهيار الأداء لكل المواقع |
| 8 | كشف معرّفات داخلية في HTML | تسريب معلومات |
| 9 | فهرسة موقع معطَّل | ضرر سمعة العميل |
| 10 | نسخة draft على نطاق عام | تسريب محتوى غير جاهز |
| 11 | `type` غير معروف يُسقط الصفحة | موقع عميل ينهار بعد رجوع إصدار |
| 12 | رسالة فشل نشر غامضة | العميل عالق بلا حل |

## 8. الاختبارات المطلوبة

**`RP-060` (MUST):** اختبار **عدم تسرب الـ draft**: تعديل في الـ draft لا يظهر على المسار العام قبل النشر. هذا اختبار حرج.

**`RP-061` (MUST):** اختبار **ذرّية النشر**: محاكاة فشل في منتصف النشر → النسخة الحية القديمة تظل تُخدَم سليمة.

**`RP-062` (MUST):** اختبار **idempotency**: نفس `Idempotency-Key` مرتين ينتج نسخة واحدة.

**`RP-063` (MUST):** اختبار **الرجوع**: النشر مرتين ثم الرجوع → الموقع يخدم النسخة الأولى فورًا.

**`RP-064` (MUST):** اختبار **التوافق الخلفي**: لقطة بـ `schemaVersion` قديم تُرندَر بنجاح بعد تحديث الـ schemas.

**`RP-065` (MUST):** اختبار **عدم التسريب**: HTML المنشور لا يحتوي `organization_id` ولا بريد المالك ولا أي معرّف داخلي.

**`RP-066` (MUST):** اختبار **الأداء**: عرض صفحة منشورة يتم بعدد استعلامات ثابت لا يعتمد على عدد الأقسام.

**`RP-067` (MUST):** اختبار E2E: إنشاء → تعديل → نشر → زيارة الدومين العام → التأكد من ظهور التعديل، ثم تعديل بلا نشر → التأكد من **عدم** ظهوره.

## 9. Definition of Done — Renderer & Publishing

- [ ] النشر غير متزامن ويرد `202` بـ `jobId`.
- [ ] `expectedDraftVersion` مدعوم و`409` عند التعارض.
- [ ] `Idempotency-Key` مدعوم ومختبَر.
- [ ] التحقق الكامل قبل بناء اللقطة.
- [ ] تبديل المؤشر ذرّي، والفشل قبله لا يمس النسخة الحية.
- [ ] اللقطة مكتفية بذاتها وتحمل `schemaVersion`.
- [ ] الإبطال للموقع المتأثر فقط.
- [ ] مفتاح الـ cache يتضمن `publishedRevisionId`.
- [ ] الرجوع يعمل فورًا ولا يمس الـ draft.
- [ ] الـ renderer يقرأ المنشور فقط — لا مسار للـ draft.
- [ ] SEO كامل: title/description/canonical/OG/sitemap/robots.
- [ ] موقع معطَّل يرد `noindex`.
- [ ] لا تسريب لمعرّفات داخلية.
- [ ] عدد استعلامات ثابت لعرض الصفحة.
- [ ] اختبار عدم تسرب الـ draft يمر.
- [ ] `audit_logs` يسجل كل نشر ورجوع.

---

## 10. ما يحتاج ADR

- تغيير استراتيجية العرض الأساسية (SSR ↔ static ↔ edge).
- السماح بأي قراءة draft من مسار عام.
- تغيير نموذج النسخ (من لقطات إلى غيره).
- بناء ملفات ثابتة منفصلة لكل موقع.
- تغيير استراتيجية الـ cache invalidation.
