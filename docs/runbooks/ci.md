## Workflow and security

`.github/workflows/ci.yml` runs on every pull request, pushes to `main`, and manual dispatch. No path filter, privileged PR event, deployment, secret input, registry push or provider activation. The workflow uses two Ubuntu 24.04 jobs: verification and images. Each has a 14-minute deadline. Tasks inside each job remain sequential with the existing conservative heap/concurrency policy. Superseded runs are canceled by workflow and PR/ref identity; unrelated PRs do not cancel each other.

Permissions are explicitly `contents: read`; all unspecified token permissions are none. Checkout uses the event's ref and verifies the fetched commit against `GITHUB_SHA`. Read-only checkout authentication exists only in that step's environment, is unset immediately after fetch, and is never persisted in Git config. Event strings are not interpolated into executable shell text. Fork PRs receive no privileged repository secrets. Repository settings must retain GitHub's restricted fork-token behavior and require review for external contributor runs.

No shared pnpm, Turbo, browser or Docker cache is uploaded/restored. Each hosted runner starts fresh. This deliberately avoids cross-trust cache poisoning; reviewed within-job Docker layer reuse is allowed. Local developer caches are not proof of a clean CI install.

The reviewed prebundled checkout/setup/upload Actions currently fail CORE-002 and are not used. Native Git, checksum-verified Node/Gitleaks, and the exact approved pnpm replace setup Actions. A small repository-owned JavaScript action invokes the official pinned Artifact SDK, with SDK output captured to prevent raw network/upload errors entering logs. The action is versioned by the exact checked-out commit, not a floating third-party ref. See [dependency review](../checkpoints/00-j-dependency-review.md). No custom artifact protocol, fork, monkey patch, override or security suppression.

Workflow/action metadata use JSON, a YAML-compatible subset, so native parsing plus strict project-specific assertions can reject unknown fields and insecure trigger/permission/command changes without adding another parser. GitHub's provider-side validation still must run after publication.

## Evidence and failure behavior

The 2026-10-12 targeted correction records platform-specific Sharp/libvips obligations in the [dependency review](../checkpoints/00-j-dependency-review.md#targeted-platform-license-correction---2026-10-12). Package name, every resolved version and declared expression must match the reviewed copyleft identity. Unknown identities fail with bounded sanitized metadata, not package paths or arbitrary raw errors. Platform-specific license inventories are not interchangeable: Windows, Ubuntu/glibc and Alpine/musl require their applicable evidence. No blanket LGPL acceptance or change to advisory thresholds is permitted.

The root CI commands clear their own previous summary, retain per-command exit status/timing and lockfile hash, and return nonzero on any failure. The test command clears its own previous native/coverage evidence before execution. Missing or empty coverage is rejected. Docker/fixture/image failures propagate; no native database fallback exists.

The upload action runs after a started gate even on failure. Evidence is limited to the current run's summary, native JSON test reports, coverage, bundle result and Playwright screenshots/traces. No `.env`, generated infrastructure directory, raw command log, Docker inspect dump or arbitrary workspace archive is uploaded. Native status/counts remain unchanged; diagnostic message/stack/actual/expected payloads are withheld. Uploads are bounded to 200 MiB total, 25 MiB per file, 5,000 files, and seven days' retention. Symlinks and unsafe archive paths are rejected. Trace contents undergo bounded inspection. Canary/credential checks and unsuppressed Gitleaks scanning must pass before upload. Unsafe evidence causes a failed upload gate, not silent publication or a successful skip. Raw rejected evidence stays local to the ephemeral runner; it is not exported.

No claim is made that sanitization detects every conceivable secret. CI receives no deployment secrets; fixture credentials are generated only in child test environments. SDK network output is withheld. Test failures may reduce diagnostic detail in published reports deliberately. If installation fails before the SDK exists, upload can fail too; native GitHub step status remains available, but no fabricated artifact success is recorded.

Per-job summaries distinguish local verification from a hosted execution. Even a hosted command's summary is not proof that the entire workflow passed: both required jobs and evidence steps must be green. Confirm actual duration under IN-033 on the first hosted run; local timing is not a hosted SLA.
